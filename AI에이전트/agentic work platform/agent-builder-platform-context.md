# 에이전트 빌더·런타임 플랫폼 검토 맥락

## 이 문서의 목적

향후 대화에서 배경을 다시 설명하지 않고, 아래 문제를 이어서 검토하기 위한 현재 시점의 맥락 기록이다.

- 비개발자가 자연어로 에이전트를 만들 수 있는 환경은 어떤 문제를 해결하는가?
- 이미 Claude Desktop과 MCP·Skill을 활용하고 있는 회사에 별도의 에이전트 빌더·런타임 플랫폼이 필요한가?
- 필요하다면 기존 환경과 구분되는 실질적 가치는 무엇이며, 한계는 무엇인가?

## 현재 회사의 상황

- Claude Desktop을 범용 에이전트 인터페이스로 사용한다.
- MCP를 통해 사내·외부 시스템과 도구에 접근한다.
- Skill을 통해 업무 지식, 절차, 기준을 Claude에 추가한다.
- 비개발자도 이 환경을 실제 업무에 활용하고 있다.
- 여기에 자연어 기반 에이전트 빌더와 별도 런타임 플랫폼을 Claude Desktop에 연결하는 방안을 검토 중이다.
- 핵심 관심사는 기능을 하나 더 만드는 것이 아니라, 이 추가 계층이 실제로 어떤 가치를 만드는지와 투자할 필요가 있는지를 판단하는 것이다.

## 에이전트에 대한 잠정 정의

> 에이전트는 주어진 목표와 허용 범위 안에서 실행 결과를 관찰하고, 다음 행동을 스스로 선택하며 일을 수행하는 시스템이다.

이 정의에서는 구현 기술보다 **실행 중 선택권이 어디에 있는가**가 중요하다.

- 정해진 노드를 정해진 순서로 실행하는 LangGraph 구성은 AI 워크플로우에 가깝다.
- 관찰 결과에 따라 LLM이 다음 행동, 사용할 도구, 추가 조사 여부, 종료 여부를 고르는 ReAct 기반 LangGraph 구성은 에이전트라고 볼 수 있다.
- 그래프 구조가 존재한다는 사실 자체는 에이전트 여부를 결정하지 않는다.
- 실제 제품에서는 결정론적 워크플로우와 동적 에이전트가 섞인 형태가 자연스럽다.
- 규정된 절차와 재현성이 중요한 업무에는 워크플로우가 오히려 더 적합할 수 있다.

## 현재의 핵심 판단

**“비개발자가 자연어로 에이전트를 만들 수 있다”는 설명만으로는 별도 플랫폼의 필요성이 충분히 입증되지 않는다.**

현재 Claude Desktop + MCP + Skill 조합만으로도 다음이 가능하기 때문이다.

- 사용자가 자연어로 업무를 요청한다.
- Claude가 여러 도구와 시스템을 사용한다.
- Skill로 반복 가능한 업무 절차와 조직의 노하우를 적용한다.
- 전문화된 업무 수행 방식을 공유하고 재사용한다.

따라서 플랫폼의 가치는 “에이전트를 만들 수 있다”가 아니라 다음 질문으로 검증해야 한다.

> 기존 환경에서는 안정적으로 맡길 수 없던 어떤 업무를, 추가 플랫폼을 통해 맡길 수 있게 되는가?

## 별도 플랫폼이 해결할 수 있는 문제 후보

다음은 가설이며, 회사에 실제 문제가 존재하는지 확인해야 한다.

| 현재의 문제 | 가능한 해법 | 별도 플랫폼 필요성 |
|---|---|---|
| 사용자가 매번 업무 방식과 기준을 다시 설명해야 함 | Skill 또는 업무 프로필 작성 지원 | 기존 환경 개선으로 해결 가능성이 큼 |
| 다른 사람이 만든 자동화를 믿고 사용하기 어려움 | 사례 기반 평가, 버전, 담당자, 변경·배포 관리 | 기존 관리 기능의 부족 여부에 따라 결정 |
| 대화가 끝나도 업무가 계속되어야 함 | 장기 실행, 상태 저장, 이벤트·API 실행, 실패 복구 | 별도 런타임의 강한 근거가 될 수 있음 |
| 중요한 단계에서 승인과 권한 통제가 필요함 | 승인 절차, 최소 권한, 정책 집행, 감사 이력 | 기존 환경이 보장하지 못한다면 강한 근거 |
| 동일 업무를 여러 사용자가 일관되게 수행해야 함 | 고정된 입력·출력 계약, 검증된 실행 버전 | 공통 운영 계층의 근거가 될 수 있음 |

## 빌더와 런타임은 분리해서 판단한다

런타임이 필요하다고 해서 자연어로 LangGraph 코드를 생성하는 빌더까지 자동으로 필요한 것은 아니다.

- **빌더**: 목적, 입력, 업무 기준, 도구, 권한, 완료 조건, 예외 처리를 정의하고 시험하도록 돕는다.
- **런타임**: 정의된 업무를 실행하고 상태, 권한, 승인, 이력, 실패와 재시도를 관리한다.

초기에는 공통 런타임에 아래 요소를 담은 업무 프로필을 등록하는 방식도 가능하다.

- 목적과 완료 조건
- 업무 지침과 판단 기준
- 사용할 도구와 데이터
- 권한 범위
- 사람에게 넘길 조건
- 출력 형식

이 방식으로 충분하다면 시각적·자연어 기반 그래프 빌더는 과도한 투자가 될 수 있다.

## 자연어 빌딩이 만들 수 있는 가치

가장 설득력 있는 가치는 다음과 같다.

> 현업 담당자가 암묵적으로 알고 있는 업무 기준을, 검증하고 반복 실행할 수 있는 정의로 전환하는 비용을 낮춘다.

좋은 자연어 빌더는 단순히 프롬프트나 코드를 생성하는 도구가 아니다. 예를 들어 “정산 이상을 찾아줘”라는 요청을 받으면 다음을 명확히 하도록 도와야 한다.

- 어떤 데이터와 기간을 볼 것인가?
- 무엇을 이상으로 판단할 것인가?
- 애매한 경우 무엇을 추가 확인할 것인가?
- 어떤 행동에는 사람의 승인이 필요한가?
- 언제 실패 또는 완료로 판단할 것인가?
- 결과를 어떤 형식으로 남길 것인가?
- 실제 사례에서 원하는 결과가 나오는가?

즉, 자연어 인터페이스의 핵심 가치는 **구현 문법의 제거**보다 **업무 명세화와 검증의 지원**에 있다.

## 예상 한계와 위험

- 자연어는 명세와 검증을 없애지 않는다. 성공 기준과 예외는 여전히 사람이 정해야 한다.
- 필요한 데이터·도구·권한이 준비되지 않으면 빌더만으로 업무를 자동화할 수 없다.
- 기존 Claude, MCP, Skill 및 조직용 기능과 상당 부분 중복될 수 있다.
- Claude가 요청을 해석한 뒤 다시 별도 범용 에이전트에 전달하면 비용, 지연, 문맥 손실, 실패 지점이 늘어난다.
- ReAct 루프를 추가하는 것만으로 품질이 좋아지지는 않는다. 반복 추론은 예측 불가능성과 운영 비용을 키울 수 있다.
- 비개발자가 만든 정의도 운영 환경에서는 권한, 승인, 테스트, 버전, 책임자의 관리가 필요하다.
- 에이전트 생성 수가 늘어나는 것과 실제 업무 성과가 좋아지는 것은 다르다.

## 권장 검증 방식

대표적인 반복 업무 하나를 선정하고, 먼저 잘 만든 `Skill + MCP`만으로 수행한다. 이후 남는 문제에 따라 투자 방향을 정한다.

- 업무 설명과 정의가 어렵다 → Skill·업무 정의 작성 지원
- 결과를 신뢰하기 어렵다 → 평가·검증·버전·배포 관리
- 사람이 계속 붙어 있어야 한다 → 장기 실행 런타임과 상태 관리
- 승인·권한·감사가 부족하다 → 정책 집행 계층
- 기존 구성으로 충분히 해결된다 → 별도 빌더 투자를 보류

비교 지표는 에이전트 생성 개수가 아니라 다음이 되어야 한다.

- 검토와 수정을 포함한 사람의 개입 시간
- 업무 단위 성공률과 오류 유형
- 실패 탐지·복구에 드는 부담
- 실행 비용과 완료 시간
- 승인 및 감사 요건 충족 여부
- 다른 사용자가 같은 품질로 재사용할 수 있는 정도

## 현재의 과제 목적 문장

> 현업 담당자가 자신의 업무 기준을 정의하고 검증하여, 조직이 반복적으로 실행·운영할 수 있는 업무 자동화로 전환하도록 지원한다.

이 목적 아래에서 업무 특성에 따라 Skill, 결정론적 워크플로우, ReAct 에이전트 또는 이들의 조합을 선택한다. 플랫폼의 성과는 어떤 형태를 얼마나 많이 만들었는지가 아니라, **이전에는 맡길 수 없던 어떤 업무를 신뢰 가능하게 맡길 수 있게 되었는지**로 평가한다.

## 다음 논의에서 답해야 할 질문

1. 현재 `Claude Desktop + MCP + Skill`로 수행 중인 대표 업무는 무엇인가?
2. 그 업무에서 사람이 반복 개입하는 지점과 실패 유형은 무엇인가?
3. 대화 밖의 장기 실행, 이벤트 실행, 상태 유지가 실제로 필요한가?
4. 현재 환경에서 권한, 승인, 실행 이력, 버전 관리는 어디까지 가능한가?
5. 자연어 빌더의 주 사용자는 업무 담당자, 업무 설계자, 운영 관리자 중 누구인가?
6. 성공을 입증할 파일럿 업무와 비교 기준은 무엇인가?

## 후속 리서치에서 구체화된 방향

- 단순 자연어 에이전트 제작·공유·예약 실행은 Claude 생태계와 중복되므로 핵심 가치로 삼기 어렵다.
- 사내 플랫폼은 Claude Desktop을 대체하지 않고, Claude가 MCP로 호출하는 **업무 실행·통제 계층**으로 포지셔닝한다.
- 가장 일반화 가능한 생산성 문제는 여러 시스템과 사람을 거치는 **예외 업무의 장시간 처리, 대기, 인계, 승인, 실패 복구**다.
- 첫 제품 패턴은 `Trigger → Context assembly → Judgment → Human gate → Action → Verification` 구조의 **예외 처리 에이전트 팩토리**가 적합하다.
- 복잡한 빌더의 필요성은 그래프 자체가 아니라 상태, 혼합 제어 흐름, 사람 개입, 실패 의미론, 정책, 평가, 운영을 명시해야 한다는 데 있다.
- 일반 사용자는 빈 그래프를 편집하기보다 자연어 인터뷰, 검증된 템플릿, 실제 사례 테스트로 업무를 정의해야 한다.
- 상세 제안은 [플랫폼 가치 제안](./agent-builder-platform-proposal.md)에 기록했다.

## 비전·아키텍처 설계에서 정리된 방향

- 플랫폼의 기본 원칙은 **Agent-first, Workflow-backed**다. 에이전트는 판단을, 워크플로우는 진행 규칙을, 런타임은 업무 생명주기를 담당한다.
- 반복 가능한 개인 업무의 원형은 **업무 플레이북**, 내부의 배포 단위는 **업무 실행 정의(Work Definition)**, 사용자에게 보이는 제품 단위는 **업무 에이전트**로 부른다.
- 실행의 기본 단위는 대화가 아니라 장기 상태를 가진 **업무 건(Case)**이다.
- 기존 Jira·Confluence·Agit·Slack·Google Workspace MCP는 에이전트의 손을 제공한다. 별도로 이벤트, 상태 저장, Queue, Identity·Token, 정책, 승인, 관측성, 평가와 같은 런타임의 신경계가 필요하다.
- 런타임은 Invocation Gateway, Durable Orchestrator, Agent Executor, Human Task Service, Tool & Policy Gateway, State·Artifact Store, Observability·Evaluation으로 구성한다.
- Claude Desktop에는 `업무 에이전트 조회`, `Case 시작·조회`, `정보 제공`, `승인`, `취소` 기능을 MCP로 노출한다.
- 상세 비전과 런타임 설계는 [비전 및 런타임 설계](./agentic-work-platform-vision.md)에 기록했다.
