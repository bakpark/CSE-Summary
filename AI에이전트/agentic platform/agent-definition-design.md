# Agent Definition MVP 설계

> 작성일: 2026-10-05. 수정일: 2026-10-06. 재검토일: 2026-10-06.
> 상태: 설계 기준. SDK 인터페이스는 구현 전 계약이다.
> 작성 기준: ASD-STE100의 원칙을 한국어에 적용했다. 공식 준수를 뜻하지 않는다.
> 관련 문서: [Agent Builder](agent-builder-design.md), [Stage Runner](agent-stage-runner-design.md).

## 1. 목적과 책임 경계

**에이전트는 고정 Java 코드베이스와 그 코드로 빌드한 Agent JAR로 전달한다. Definition은 저장·버전과 빌드 산출물 연결을 담당한다.**
별도 실행 DSL, 정의 해석기, 독립 Definition 서버는 만들지 않는다.

| 담당 | 소유할 작업 |
| --- | --- |
| Builder 백엔드 | 편집 그래프 검사, Java 그래프 코드 생성, 코드 노드 편집 틀 생성 |
| Definition 모듈 | 소유자 확인, 편집본 저장, 버전 고정, 버전 조회·빌드 상태·등록 JAR 연결 |
| Runner 제어 서비스 | 버전 선택, 세션 생성·종료, 컨테이너 관리, 메시지 전달 |
| Agent CI 연계 | 저장 후 빌드 요청, 고정 코드 컴파일·검증, 사내 Registry 등록, 빌드 결과 반영 |
| Runner 실행 어댑터 | 등록 JAR·SDK 확인, 진입점 호출, 준비 상태와 실행 결과 전달 |
| SDK | 그래프 구성·실행, 공통 노드, 코드 노드 계약, 대화 상태, 환경 연결 |

Builder 백엔드와 Definition은 기존 플랫폼 백엔드에 둔다.
Definition은 코드를 생성하거나 그래프를 검사하지 않는다.
Runner는 코드를 변경하거나 다시 생성하지 않는다.
SDK는 플랫폼의 저장과 버전을 관리하지 않는다.
테스트 채팅 UI는 Builder 화면에 배치한다. 실행 계약은 Runner 설계를 따른다.

### 연계 세부 계약의 확정 필요

컴포넌트의 책임과 연계 흐름은 이 문서를 따른다.
세부 계약은 구현 전에 세 문서에서 같은 기준으로 확정해야 한다.

- 연계 API의 요청·응답 필드와 오류 코드
- SDK 인터페이스의 실제 타입과 메서드 서명
- 모델·도구 ID와 환경 연결의 매핑 규칙

현재 예시와 설명은 최종 API 명세가 아니다.
이 항목은 후속 확정 사항이며 MVP 기능 범위를 추가하지 않는다.

## 2. 편집본과 고정 코드베이스

편집본은 캔버스 그래프와 코드 노드의 Java 소스를 포함한다.
연결과 코드가 미완성이어도 저장할 수 있다.
저장은 파일 형식·경로·크기만 검사한다.
테스트 준비 시 실행 가능한 코드베이스를 만든다.

```text
agent.json                     진입점과 SDK 버전
src/agent/PaymentAgent.java     Builder가 생성한 그래프 구성 코드
src/agent/nodes/Normalize.java  사용자 메서드 본문을 포함한 코드 노드
editor/flow.json                캔버스 편집 정보
```

```json
{
  "entryClass": "agent.PaymentAgent",
  "sdkVersion": "<고정 사내 SDK 버전>"
}
```

플랫폼은 에이전트 ID, 이름, 소유자, 저장 순번, 버전 ID를 관리한다.
이 정보와 자격증명은 agent.json에 넣지 않는다.
MVP는 Java 17과 SDK 버전 하나를 지원한다.
사용자별 빌드 설정과 외부 라이브러리는 받지 않는다.

### 작성 권한

| 대상 | 기준 |
| --- | --- |
| 그래프와 노드 설정 | 사용자가 캔버스 또는 자연어로 수정한다. |
| 그래프 구성 코드 | Builder 백엔드만 생성한다. 사용자 직접 편집은 제공하지 않는다. |
| 코드 노드 본문 | 사용자가 직접 또는 자연어로 수정한다. 해당 Java 파일에만 보관한다. |
| 클래스·메서드 틀 | Builder가 고정 틀을 사용한다. 사용자가 서명과 패키지를 바꾸지 않는다. |
| editor/flow.json | 노드 ID와 코드 파일 경로를 참조한다. 코드 본문을 중복 저장하지 않는다. |

**편집 단계의 기준은 그래프와 코드 노드다. 실행 단계의 기준은 고정한 Java 코드다.**
저장 후 빌드 준비에서 Builder가 저장된 그래프의 구성 코드를 생성한다.
Definition은 생성 코드를 비교하거나 재생성하지 않는다.
같은 버전에 원본 그래프와 생성 코드·노드 코드를 함께 저장한다.
SDK는 editor/flow.json을 읽지 않는다.
개발자가 인계 코드를 서비스에서 수정해도 Builder에 자동 역반영하지 않는다.

## 3. SDK의 최소 실행 계약

LangGraph4j는 노드와 연결로 그래프를 구성하고 실행 그래프로 컴파일한다.
SDK는 이 기능을 내부에서 사용한다.
근거: [LangGraph4j 1.8 코어 문서](https://langgraph4j.github.io/langgraph4j/1.8/core/core-library/).
공개 계약에는 사내 타입과 JDK 타입만 사용한다.
SDK의 그래프 API는 MVP 노드·직렬 연결·조건 분기를 위한 얇은 어댑터로 제한한다.
범용 그래프 엔진을 새로 만들지 않는다.

아래 서명은 제안이다. 실제 SDK 구현에서 같은 역할로 확정한다.

```java
interface AgentProgram {
    AgentSession open(AgentEnvironment environment);
}
interface AgentSession {
    AgentReply invoke(String message);
}
interface AgentNode {
    Map<String, Object> apply(Map<String, Object> input);
}
```

진입점 클래스는 AgentProgram을 구현하고 인자 없는 생성자를 제공한다.
open은 그래프를 준비하고 빈 대화 상태의 AgentSession을 반환한다.
invoke는 메시지 하나를 처리한다. 같은 세션에서 순서대로 호출한다.
AgentReply는 최종 답변과 도구 호출 요약을 제공한다.
AgentEnvironment는 LLM·도구 연결 구현을 제공한다. 자격증명을 코드에 넣지 않는다.
생성 코드는 선택한 모델 ID와 도구 ID를 참조한다.
Runner와 서비스의 환경 연결은 같은 ID를 실제 호출 구현으로 연결한다.
그래프 준비 시 미등록·미허용 ID를 거부한다.
SDK의 공통 Agent 노드만 도구를 호출한다. Function은 환경 연결을 받지 않는다.
Runner와 서비스는 같은 등록 Agent JAR·진입점·SDK를 사용하고 환경 연결만 교체한다. 소스 코드는 기존 저장소에 함께 유지한다.

코드 노드는 입력 Map을 읽고 JSON 값으로 구성한 결과 Map을 반환한다.
코드 노드의 일반 예외는 실행 오류로 반환한다.
클래스 틀에는 JDK와 사내 SDK의 고정 import만 제공한다.
예시 본문은 다음과 같다.

```java
String request = (String) input.getOrDefault("request", "");
return Map.of("request", request.trim());
```

첫 노드의 입력은 현재 메시지의 request다.
다음 노드의 기본 입력은 직전 노드의 결과다.
명시적 입력 연결은 MVP에서 제공하지 않는다.
Condition은 직전 결과의 필드 하나와 값의 동등 비교만 지원한다.
분기 합류는 실제 선택한 경로의 직전 결과를 사용한다.
프롬프트는 request와 previous.output 참조만 지원한다.
LLM·Agent·Reply의 결과는 output 필드를 사용한다.
SDK는 노드의 입력을 읽기 전용으로 제공한다.
JSON 값은 문자열·숫자·불리언·null·목록·문자열 키 Map으로 제한한다.
코드 노드는 null Map이나 Java 객체를 결과로 반환할 수 없다.
없는 필드를 참조하면 실행 오류로 처리한다. 빈 값으로 자동 대체하지 않는다.
Reply는 최종 문자열을 반환한다. 직전 결과를 사용할 때는 output이 문자열이어야 한다.
Function 뒤의 LLM은 previous.output을 쓰려면 Function 결과에 output을 넣어야 한다.
코드 노드 편집 화면은 이 기본 입력·결과 예제를 표시한다.

SDK는 현재 세션의 사용자·답변 대화 이력을 메모리에 유지한다.
한 턴이 성공하면 사용자 메시지와 최종 답변 한 쌍을 이력에 추가한다.
중간 LLM 결과와 도구 메시지는 해당 턴 안에서만 사용한다.
실패한 턴은 확정 대화 이력에 추가하지 않는다.
LLM·Agent 공통 노드는 이 이력을 사용한다.
각 턴의 임시 노드 결과는 다음 턴에 넘기지 않는다.
코드 노드는 별도 세션 변수나 DB를 관리하지 않는다.
직렬 흐름과 조건 분기만 지원한다. 반복 도구 호출은 공통 Agent 노드 내부에서 제한한다.

## 4. 저장·버전·전달 계약

| 작업 | 입력 | 결과 |
| --- | --- | --- |
| 생성 | 이름 | 에이전트 ID와 빈 편집본 |
| 저장 | 에이전트 ID, 예상 순번, 그래프·코드 노드 | 새 저장 순번 |
| 고정 | 에이전트 ID, 저장 순번, 저장 기반 요청 ID | 생성 코드를 포함한 버전 ID |
| 빌드 요청 | 버전 ID, SDK 버전, 요청 ID | buildId와 빌드 상태 |
| 빌드 결과 연결 | 버전 ID, buildId, artifactRef, 체크섬, SDK 버전 | 검증한 등록 산출물 메타데이터 |
| 조회 | 에이전트 ID 또는 버전 ID | 편집본 또는 고정 코드베이스 |
| 등록 산출물 조회 | 버전 ID | 성공한 Nexus GAV·SDK 버전·SHA-256 |

저장 완료로 발생한 빌드 준비의 버전 고정 요청은 다음 순서로 처리한다.

1. 플랫폼 백엔드는 요청한 순번의 저장본을 읽는다.
2. Builder 백엔드는 그래프를 검사하고 구성 코드를 생성한다.
3. Definition은 저장 순번을 다시 확인한다.
4. 순번이 같으면 전체 코드베이스를 원자적으로 고정한다.
5. 순번이 다르면 충돌을 반환한다. 사용자에게 다시 저장하도록 알린다.

파일은 코드베이스 내부의 상대 경로만 허용한다.
같은 요청 ID의 재전송은 같은 버전을 반환한다. 다른 입력으로 키를 재사용하면 거부한다.
검사와 코드 생성에 실패하면 버전을 만들지 않는다.
Java 문법과 SDK API 적합성은 Jenkins Agent CI에서 확인한다. 컴파일·등록 실패는 고정한 소스를 변경하지 않는다. Runner는 버전 ID와 연결된 정확한 Agent JAR를 실행하며 코드를 다시 생성하거나 컴파일하지 않는다. 개발자는 같은 등록 JAR를 사용한다. 사용자 ZIP 기능은 현재 작업 계획에서 제외한다.

### 빌드 산출물 연결

저장 성공과 빌드 요청 상태를 기존 저장소에 함께 기록한다. 요청 전달 실패는 표시하고 같은 고정 버전으로 재요청할 수 있다. 별도 분산 큐·새 CI 플랫폼을 구축하지 않는다.

- 저장 순번, 버전 ID, buildId, SDK 버전으로 소스와 빌드를 연결한다.
- 성공한 산출물에는 사내 Nexus의 정확한 artifactRef와 SHA-256을 기록한다. 가변 latest·SNAPSHOT 참조로 시험하지 않는다.
- CI 결과는 인증된 연계 경로로만 반영한다. 일치하지 않는 버전·SDK·buildId, 취소되거나 오래된 시도의 결과를 최신 빌드로 반영하지 않는다.
- 등록 성공과 실제 산출물 확인이 끝나야 라이브러리를 READY로 표시한다. 임의 URL이나 사용자가 입력한 산출물 메타데이터를 신뢰하지 않는다.
- 빌드 시도 기록과 실행 세션은 구분한다. 빌드 메타데이터를 보관해도 대화·시험 이력을 영구 저장하는 것은 아니다.
- Jenkins와 Nexus를 사용한다. artifactRef는 기존 사내 Maven 저장소의 repositoryId·groupId·artifactId·불변 version 좌표로 표현하는 안이다. 실제 저장소·좌표 규칙·Jenkins job 및 credential ID는 기존 운영 설정으로 확정한다.

## 5. 최소 라이프사이클

```text
편집·저장 → 검사·코드 생성·버전 고정 → Agent CI → Registry 등록
    ↑                                                |
    └──────── 수정·재빌드 ───── Runner JAR 시험 ←──────┘
                               |
                         서비스 통합·기존 배포
```

새 저장본의 코드 변경이 새 버전과 빌드를 만든다. 시험 시작과 같은 버전의 새 대화는 CI를 다시 호출하지 않는다. 기존 소스 버전과 성공한 등록 산출물은 이후 편집으로 바뀌지 않는다. 승인·승격 단계를 추가하지 않는다.

CI 성공은 진행 중 대화를 자동으로 변경하지 않는다. 제작자가 수정본 테스트를 요청하면 준비된 새 JAR로 빈 세션을 연다.

인수 개발자는 같은 Agent JAR와 SDK를 서비스 내부에서 실행한다. 필요 시 고정 소스를 기존 저장소에서 수동 전달받는다. 서비스 통합·Git 반영·배포는 기존 절차를 사용한다. 사용자 ZIP 다운로드는 이전 삭제 요청에 따라 현재 작업 범위에서 제외한다.

## 6. 최소 구현 범위

| 담당 | 구현 작업 |
| --- | --- |
| SDK | 진입점·세션·코드 노드·환경 연결 계약과 MVP 공통 노드 |
| Builder | 그래프 검사, 코드 생성 템플릿, 메서드 본문 편집, 오류 위치 연결 |
| Definition | 소유자 검사, 편집본 저장, 순번 충돌, 버전 고정·조회·빌드 메타데이터 |
| Agent CI | 고정 소스·SDK로 컴파일·검증, Agent JAR 등록, 결과 연결 |
| Runner | 등록 JAR·SDK 확인, 격리 로딩, 세션 실행·종료 |

독립 관리 서비스, 실행 DSL, 시험 이력 DB, 승인 흐름은 구현하지 않는다.
전체 코드 역변환, 버전 병합, Git 자동화, 운영 배포 관리도 구현하지 않는다.

## 7. 완료 기준

- 미완성 편집본을 저장하고 다시 열 수 있다.
- 코드 노드를 수정한 뒤 그래프를 다시 생성해도 본문이 유지된다.
- 저장 충돌과 오래된 버전 고정 요청을 거부한다.
- 저장 순번·소스 버전·buildId·등록 JAR가 연결되고 Runner가 그 JAR를 사용한다.
- 빌드·등록 실패를 READY로 표시하지 않는다. 늦은 빌드 결과가 새 버전에 연결되지 않는다.
- 수정 후에도 이전 버전의 코드가 유지된다.
- 같은 Agent JAR와 SDK를 Runner·Java/Kotlin 샘플 서비스에서 실행한다.
- 조건 분기, 코드 노드 결과, 두 턴의 대화가 같은 의미로 동작한다.
- 잘못된 노드 결과와 없는 모델·도구 참조를 명확한 오류로 처리한다.
