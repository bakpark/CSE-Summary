# Agent Playground 컴포넌트 구현 작업 초안

> 목적: Builder·Definition·Stage Runner 설계를 통합해 구현 티켓과 인수조건을 정의한다.
> 상태: MVP 범위·계약·일정을 재검토한 초안. 역할 A·B·C와 일정은 실제 담당자 배정 전 가안이다.
> 작성일: 2026-10-05.
> 기준 문서: [Builder MVP 설계](agent-builder-design.md), [Definition MVP 설계](agent-definition-design.md), [Stage Runner MVP 설계](agent-stage-runner-design.md).
> 사용자 관점 참고: [사용자 시나리오](agent-playground-user-scenarios.md).

**편집 단계의 기준은 그래프와 Java 코드 노드이고, 실행 단계의 기준은 고정한 Java 코드베이스다.** Builder가 서버 저장본에서 구성 코드를 생성한다. Definition이 원본과 생성 코드를 원자적으로 고정한다. Runner와 적용 서비스는 같은 진입점과 SDK를 사용한다. 파일럿 작업은 별도 묶음으로 관리한다.

## 책임과 범위

| 컴포넌트 | 담당 | 이번 구현에서 맡지 않는 작업 |
| --- | --- | --- |
| SDK | LangGraph4j의 얇은 어댑터, 진입점·세션·공통 노드·Java 코드 노드·환경 연결 | 플랫폼 저장·버전 관리, editor/flow.json 해석, 독자 그래프 엔진 |
| Builder | 기존 Flowise 기반 프로토타입 재사용, 편집·그래프 검사·Java 코드 생성·오류 위치 표시 | 코드 실행, 버전 저장, 전체 Java 편집·역변환 |
| Definition 모듈 | 소유자 확인, 편집본 저장, 저장 순번 충돌, 고정 코드베이스 조회 | 그래프 검사·코드 생성, 독립 서버, 실행 DSL |
| Runner 실행 어댑터 | SDK 검사·Java 컴파일·open/invoke·결과 전달 | 코드 수정·재생성, 버전 저장 |
| Runner 제어 서비스 | 준비 요청·버전 고정 요청·세션·컨테이너·메시지·정리 | 그래프 생성, SDK 대화 상태의 영구 보관 |
| 테스트 채팅 UI | Builder 화면의 별도 시험 패널 | Builder 제작 대화와 시험 대화의 혼합, 과거 대화 조회 |
| 인수 개발자 | 산출물의 서비스 저장소 반영·통합 검증·기존 CI/CD 배포 | Playground를 통한 운영 서비스 자동 배포 |

세 설계에서 명시한 MVP를 기본 범위로 삼는다. 기존 삭제 요청 AP-01·03·21·23·22·11·04·28 중 승인·조사·KPI·공유·별도 KPAP 확장·제공 준비 작업은 재등록하지 않는다. 설계의 ZIP 다운로드는 AP-22 삭제 요청에 따라 작업 목록과 합계에서 제외한다. 파일럿은 수동 고정 파일 전달로 검증한다.

새 요구는 일반 DSL 제작이 아니라 Java 코드베이스 제작이다. 이전의 CCAB 별도 연계 티켓은 제거하고, Builder 설계가 지정한 프로토타입의 자연어 편집과 캔버스를 재사용한다. Flowise 원본 실행 서버는 설치하지 않는다.

## 산정과 일정 가정

- **1 SP = 1인일.** 해당 작업의 구현과 기본 개발 검증을 포함한다. 여러 컴포넌트의 통합·장애·성능 검증은 VAL 티켓으로 별도 산정한다.
- 개발자 3명, 10월 12일 착수, 11월 18일 파일럿 검증 완료, 11월 20일 결함 수정 포함 완료를 목표로 한다. 모든 완료일시는 **2026년 한국시간 18:00** 기준의 가안이다.
- 기존 저장소·인증·LLM 및 시험 도구 Gateway·컨테이너 생성과 종료 기반을 사용할 수 있다고 가정한다. 신규 인프라·업무 API 개발은 제외한다.
- Agentflow 패키지는 프로토타입의 현재 버전으로 고정하고, Java 17·SDK 한 버전·고정 이미지 하나를 지원한다.
- 선행 열은 계약 선공유와 구현 완료 의존성을 구분한다. WEB·CTL 병렬 개발은 먼저 공유한 API와 대역을 사용하며, 상대 컴포넌트 구현 이전에는 통합 완료로 판정하지 않는다. 아래 역할별 작업일 배정으로 중복 투입을 확인했다. 실제 담당자 배정은 아직 필요하다.
- ID는 아직 Jira에 등록하지 않은 초안 식별자다. 기존 ID를 가능한 유지하되 제목·내용은 이번 설계 기준으로 교체한다.

### 역할별 작업일 배정

역할 A·B·C는 각각 개발자 한 명의 전일 투입을 가정한다. C는 UI를 주로 맡되 초기 그래프 검사와 기존 CI 연결도 수행할 수 있는 개발자여야 한다. 업무 담당자는 개발자 3명과 별도로 파일럿 데이터와 설정에 참여한다.

날짜 구간의 토요일·일요일은 작업일에서 제외한다. 회사 휴무·겸무는 아직 반영하지 않았다. 날짜 구간에서 한 역할에 두 티켓의 작업일을 겹쳐 배정하지 않았다.

| 역할 | 순서별 작업일 배정 | 작업량 |
| --- | --- | ---: |
| A · SDK·생성·고정 | SDK-01 10/12~14 → SDK-02 10/15~19 → SDK-04 10/20~23 → BLD-05 10/26~28 → DEF-02 10/29~11/02 → SDK-03 11/03~04 → TOOL-01 11/05 → CTL-03 11/09~11 → PIL-03 지원 11/17 | 23인일 |
| B · 저장·Runner | DEF-01 10/12~14 → RT-01 10/15~19 → CTL-04 10/20~22 → RT-02 10/26~28 → RT-03 10/29~11/02 → CTL-01 11/03~06 → CTL-02 11/09~11 → VAL-02 11/12~13 | 24인일 |
| C · Builder·UI·통합 | BLD-04 10/12~13 → BLD-01 10/15~20 → BLD-03 10/21~23 → BLD-02 10/26~28 → DEV-01 10/29~30 → BLD-06 11/03~04 → WEB-01 개발 11/05~09 → WEB-02 개발 11/10~11 → VAL-01 11/12~16 → PIL-03 11/17~18 | 26인일 |
| 업무 담당자 · 파일럿 | PIL-01 10/12~13 → PIL-02 11/10~11 | 4인일 |
| A·B·C · 수정 여유 | 각 11/19~20 | 6인일 |

WEB-01은 구현 작업 3일과 **최종 통합 완료 11/11**을 구분한다. CTL-02 완료 전에는 실제 메시지 계약의 완료를 선언하지 않는다. WEB-02·CTL-03·PIL-02도 공유된 계약과 준비된 기능으로 병렬 진행한 뒤 11/11에 통합 판정한다.

### 완료 판정과 범위 변경

11/18은 모든 인수조건과 필수 검증이 통과한 경우의 파일럿 검증 목표일이다. 발견한 차단 결함은 11/19~20 여유 안에서 수정·재검증한다. 인프라가 늦거나 파일럿에 신규 코딩이 필요하면 범위나 일정을 다시 계산하며, 실패를 통과로 바꾸지 않는다.

Java 본문 편집·6개 노드·자연어 편집을 유지한 현재 배정에서는 C의 후반 통합·사용자 검증이 종료일을 결정한다. 더 앞당기려면 인력을 늘리거나 이 MVP 기능 자체를 줄여야 한다. 단순히 인수조건이나 검증을 삭제해서 날짜를 당기지 않는다.
