# Agent Playground 산출물과 형상관리

> 작성일: 2026-10-07. 상태: 상위 기획의 상세 설계안.
> 관련 문서: [기획 초안](./agent-playground-draft.md), [Python SDK 스펙](./agent-sdk-spec.md).

## 1. 산출물과 형상관리

**Playground 형상과 실제 서비스 형상은 독립적으로 관리한다.** Playground는 KPAP의 별도 GitHub 저장소를 사용한다. 개발자의 로컬은 실제 서비스 프로젝트의 작업 공간이다. Plugin이 두 형상 사이의 import와 변경점 공유를 제공한다.

| 대상 | 관리 기준 |
| --- | --- |
| 실제 서비스 형상 | 기존 서비스 저장소에서 개발·검토·배포한다. Playground의 형상과 별도로 유지한다. |
| Playground 기준 형상 | SDK 또는 plugin으로 가져온 에이전트 정의·필요 소스·의존성·실행 정보를 고정한다. 출처와 정확한 내용을 기록한다. |
| Playground 실험 형상 | 가져온 기준 형상에서 파생한다. 허용 설정 변경과 실험 이력을 자체 저장소에 기록한다. |
| 실행·평가 결과 | 정확한 실험 형상과 패키지에 연결한다. 테스트 셋·평가 기준·시험 조건을 기록한다. |
| 개발자에게 공유할 변경 | 실험의 기준 형상과 선정 실험을 비교한다. 변경 전·후 값과 평가 근거를 전달한다. |

새 import는 새 기준 형상을 만든다. 기존 실험은 이전 기준 형상을 유지한다. 세 역할은 같은 Playground 버전 링크로 산출물과 평가 결과를 확인한다.

개발자는 현재 서비스 로컬과 제안 변경을 비교한다. 필요한 변경만 적용하고 서비스 테스트를 수행한다. Plugin은 기준 파일과 다른 로컬 변경을 충돌로 표시한다. 임의 Python 코드를 자동 역수정하지 않는다.

## 2. 라이프사이클 도식

![독립된 서비스 저장소와 Playground 저장소를 plugin의 import와 변경점 공유로 연결하는 흐름](./diagrams/agent-playground-lifecycle.png)

가져오는 방향은 에이전트 형상 import다. 돌아오는 방향은 변경점과 평가 근거 공유다. 개발자는 실제 프로젝트에서 반영 여부를 결정한다.

수정본은 새 세션에서 시험한다. 기존 대화는 기존 형상을 유지한다. 서비스에 일부만 반영한 경우, 이전 실험 결과를 서비스 버전의 검증 결과로 사용하지 않는다.

## 3. Import 계약

SDK 또는 plugin의 import 단위는 실행 가능한 에이전트 묶음이다. SDK 정의, 필요한 Python 소스, 고정 의존성, 실행 정보와 공개 설정을 포함한다. 개발자는 서비스 프로젝트에서 이 범위를 선택한다.

Plugin은 다음 정보를 기록한다.

| 항목 | 목적 |
| --- | --- |
| 에이전트 ID와 import ID | 어떤 에이전트의 어떤 가져오기인지 구분한다. |
| 서비스 출처와 파일 대응 | 저장소·에이전트 경로·원래 설정 위치를 식별한다. |
| 출처 커밋과 미커밋 여부 | 개발 이력과 가져온 로컬 상태를 구분한다. |
| 가져온 내용의 해시 | 미커밋 변경을 포함한 정확한 에이전트 내용을 식별한다. |
| Playground 커밋과 경로 | 자체 저장소에서 고정 기준 형상을 찾는다. |

출처 커밋만으로 로컬 형상을 식별하지 않는다. 미커밋 변경이 있으면 내용 해시와 실제 import 내용을 함께 보관한다. 자격증명은 가져오기 대상에서 제외한다.

새 import는 새 기준 형상으로 기록한다. 이전 기준 형상과 실험을 덮어쓰지 않는다. 사용자 작업본은 특정 기준 형상에 연결한다. 시험은 고정 Playground 커밋과 패키지로 수행한다.

## 4. 실험과 변경점 공유

기획자는 기준 형상의 허용 설정을 바꾼다. AI 엔지니어는 평가를 구성하고 설정을 실험한다. 코드 개선은 실제 서비스 프로젝트에서 수행하고 새 형상을 import한다.

평가 결과는 Playground 실험 커밋·패키지·테스트 셋·평가 기준·시험 조건에 연결한다. 로그 원문과 평가 데이터는 해당 저장 서비스에 보관하고 Git에는 참조를 기록한다.

Plugin은 **실험의 기준 import와 선정 실험 사이의 차이**를 공유한다. 서비스 저장소 전체와 Playground 저장소 전체의 차이를 사용하지 않는다.

공유 내용은 다음과 같다.

- 기준 import ID와 선정 실험 버전.
- 설정 필드와 변경 전·후 값.
- 평가 결과와 실행 기록의 링크.
- 실제 서비스의 설정 파일 또는 코드 위치와 대응 정보.

초기에는 공개 설정의 변경점을 공유한다. 코드 변경 공유를 추가하려면 Playground 소스와 실제 서비스 소스의 대응 규칙을 별도로 정의한다.

## 5. 실제 프로젝트에서의 반영

개발자는 plugin으로 변경점을 확인한다. 로컬 작업 공간과 서비스 저장소는 그대로 유지한다.

현재 값이 import 당시 값과 같고 스키마가 맞으면 선택 적용을 지원할 수 있다. 값·코드·스키마가 달라졌으면 충돌을 표시한다. 개발자는 AI 엔지니어와 반영 방법을 결정한다.

예를 들어 import 당시 검색 개수는 5다. 기획자는 이를 10으로 실험한다. 현재 서비스 로컬이 이미 8로 바뀌었다면, plugin은 5 → 10 제안과 현재 값 8을 함께 보여준다. 현재 값을 조용히 덮어쓰지 않는다.

원래 설정이 Python 코드에서 생성되는 경우에는 변경 제안을 보여준다. 임의 Python 코드를 자동 역수정하지 않는다. 직접 적용은 설정 파일과 경로가 명확한 항목부터 지원한다.

반영 후에는 실제 서비스 테스트와 기존 검토·배포 절차를 수행한다. Playground 평가가 서비스 검증을 대신하지 않는다. 일부만 반영하거나 구현·환경이 달라졌으면 이전 평가를 새 서비스 버전의 결과로 사용하지 않는다.

반영 결과를 다시 시험하려면 새 import를 수행한다. 이 과정은 개발자가 선택한다. 서비스 반영과 Playground import를 자동 동기화하지 않는다.

## 6. 구현 범위와 후속 계약

Phase0는 자체 형상 저장, import 형식, 고정 실행·평가와 수동 변경 공유를 제공한다. Phase1은 Builder 편집과 plugin의 import·변경 비교·선택 적용을 제공한다.

Playground의 Git 접근은 플랫폼이 처리한다. 사용자에게 별도 Git 조작을 요구하지 않는다. 실제 서비스 저장소의 병합·배포 절차는 기존 방식으로 유지한다.

후속 설계에서 다음을 확정한다.

- KPAP 저장소의 에이전트별 경로와 작업 공간 구성.
- import 대상 선정과 서비스 파일 대응 규칙.
- 실험 저장 충돌, 조회 권한과 보존 기간.
- 자동 적용 가능한 설정 형식과 로컬 충돌 표시.
- Playground 커밋·buildId·패키지·평가 결과 연결.

기존 Java Definition·Lifecycle 문서의 실행 계약은 Python SDK 기준으로 조정한다. 이번 방안은 별도 Playground 저장소와 plugin 교환 경로를 추가한다.
