# Agent Playground 기획

> 작성일: 2026-10-07. 상태: 상위 기획 초안.
> 작성 기준: [ASD-STE100](https://www.asd-ste100.org/STE_faq.html)의 작성 원칙을 한국어에 적용했다. 공식 준수를 뜻하지 않는다.

## 1. 개요

### 추진 배경

기획자는 업무 흐름을 정의하고 개발자는 이를 에이전트로 구현한다. AI 엔지니어는 실행 결과를 평가한다. 작업 공간이 나뉘면 기획 의도, 구현한 흐름, 평가 결과를 함께 검토하기 어렵다. 플로우 변경 요청과 실험 결과를 개발자에게 전달하는 과정도 반복된다.

### 목적과 범위

**Agent Playground는 기획자·AI 엔지니어·개발자가 에이전트 플로우를 함께 개선하는 협업 공간이다.** 세 역할은 같은 기준 형상에서 실험 버전을 만들고 결과와 변경 제안을 공유한다. 개발자는 제안을 검토하고 반영 여부를 결정한다.

기획자는 Builder에서 허용된 노드를 추가·삭제하고 연결·분기를 수정한다. 프롬프트와 설정도 변경한다. AI 엔지니어는 변경한 흐름을 평가한다. 개발자는 변경사항과 근거를 실제 서비스 형상과 비교해 반영 여부를 결정한다.

대상은 공통 실행 계약을 지원하는 에이전트다. 첫 SDK 언어는 Python이다. 사용자 구현은 내부 코드를 보존한 구성 요소로 연결한다. 개발자는 편집 가능한 범위를 정의하고 기존 절차로 서비스를 통합·배포한다.

초기 플로우 편집은 등록된 노드의 직렬 연결과 조건 분기를 지원한다. 반복·병렬 편집은 후속 범위다. 사용자 코드 내부 수정은 개발자가 담당한다.

협업은 각자의 작업본과 고정 실험 버전을 공유하는 방식이다. 같은 작업본을 실시간으로 동시 편집하는 기능은 초기 범위에 포함하지 않는다.

## 2. 타겟 사용자

| 사용자 | 주요 요구 | 역할 |
| --- | --- | --- |
| 서비스 기획자 | 업무 의도를 플로우로 직접 표현하고 실험한다. | 시험 사례와 품질 기준을 정의한다. 노드·연결·분기·설정을 편집하고 개선안을 제안한다. |
| AI 엔지니어 | 같은 기준으로 흐름 변경의 효과와 실패 원인을 확인한다. | 테스트 셋과 평가 방법을 관리한다. 기획자와 실험을 검토한다. 코드 개선은 실제 서비스 프로젝트에서 수행한다. |
| 백엔드 개발자 | 기획자의 변경 의도와 평가 근거를 실제 코드와 비교한다. | 에이전트를 구성 요소로 제공한다. 편집 범위를 정하고 제안을 검토·반영한다. 실제 서비스 형상을 관리한다. |

세 역할은 개선안을 함께 검토한다. 실제 서비스 반영 여부는 해당 에이전트의 소유 개발자가 결정한다.

## 3. 목표와 기대효과

**플로우 편집·실험·평가·변경 제안을 같은 공간에서 이어간다.** 기획 의도를 실행 가능한 흐름으로 확인하고 개발 검토에 필요한 근거를 공유한다.

| 목표 | 기대효과 | 성과 확인 지표 |
| --- | --- | --- |
| 기획자와 개발자가 같은 플로우로 개선안을 검토한다. | 기획자는 직접 흐름을 수정하고 AI 엔지니어와 결과를 확인한다. 변경 의도를 설명하고 실험 결과를 전달하는 대기를 줄인다. | 에이전트 개선·평가 주기 소요 시간 |
| 공통 시험 환경에서 변경한 흐름을 검증한다. | 사내 모델·시험 도구·고정 실행 환경을 연결한다. 세 역할이 같은 조건에서 변경 효과와 실패 원인을 확인한다. | 에이전트 수정 후 품질 검증 소요 시간 |
| 실험 변경사항과 평가 근거를 개발자의 검토로 연결한다. | 개발자는 노드·연결·분기·설정의 변경과 실험 결과를 함께 확인한다. 제안별 반영 여부와 이유를 기록한다. | 실험 변경 제안 검토 완료율 |

전체 개선·평가 주기는 결과 지표다. 품질 검증 시간은 그 안의 병목을 확인하는 지표다. 검토 완료율은 제안이 기한 내 검토되는지 확인한다. 시간 단축의 효과는 평가 범위와 품질 기준을 유지한 비교에서 판단한다.

## 4. 컴포넌트 구성

| 컴포넌트 | 책임 |
| --- | --- |
| Agent Spec·Python SDK | SDK와 Builder가 공유하는 플로우·구성 요소·편집 권한을 정의한다. SDK 실행기는 선택한 Spec을 실행한다. |
| Playground 형상·빌드 관리 | 기준 형상·플로우 변경·실험 버전을 관리한다. KPAP의 별도 GitHub 저장소를 사용하고 실행 패키지를 고정한다. |
| Stage Runner | 선택한 Spec과 고정 코드 패키지를 SDK로 실행한다. 격리 환경과 세션을 관리한다. |
| 평가 도구 | Langfuse로 실행 기록과 평가 결과를 버전에 연결한다. 고정 테스트 셋과 시험 조건으로 버전을 비교한다. |
| Agent Builder | 노드·연결·분기·설정을 편집한다. 기준 흐름과 변경 흐름, 시험 결과를 함께 보여준다. |
| 개발자 plugin | 에이전트 실행 묶음을 가져온다. 기준 형상과 선정 실험의 차이 및 평가 근거를 실제 프로젝트의 로컬에서 보여준다. |

형상 동기화는 에이전트 정의·필요 소스·의존성·실행 정보를 Playground에 가져오는 작업이다. SDK와 plugin은 같은 교환 형식을 사용한다. 실제 서비스 저장소와 Playground 저장소는 별도로 관리한다.

상세 계약은 [Python SDK 스펙](./agent-sdk-spec.md)과 [산출물·형상관리 문서](./agent-playground-collaboration-lifecycle.md)를 따른다. [기존 Runner 설계](./agent-stage-runner-design.md)의 Java 실행 계약은 Python SDK 기준으로 조정한다.

## 5. 단계별 로드맵

각 Phase의 예상 개발 기간은 6주다. Phase0를 1~6주, Phase1을 5~10주에 배치한 예시다. 공통 계약을 확정한 뒤 두 단계의 개발을 일부 병행한다. 실제 일정은 투입 인원과 파일럿 결과로 정한다.

### 5.1 Phase0 · SDK 실행과 평가 · 6주

**목표:** SDK 에이전트를 공통 시험 환경에서 실행하고 형상·기록·평가 결과를 공유한다.

개발 대상은 Agent Spec·Python SDK, Playground 형상·빌드 관리, Stage Runner, 평가 도구다.

#### 시나리오 A · 개발자의 SDK 에이전트 시험

1. 개발자는 실제 서비스 프로젝트에서 SDK로 에이전트를 구현한다.
2. 개발자는 SDK로 정의·소스·고정 의존성을 내보내고 Stage에 제출한다. 플랫폼은 기준 형상을 고정하고 준비 상태를 반환한다.
3. 플랫폼은 CI에서 고정 코드 패키지를 만들고 시험 환경을 준비한다. 개발자는 준비 완료 후 세션을 열어 메시지와 후속 대화를 시험한다.
4. 개발자는 코드를 수정해 새 버전을 제출한다. 플로우·설정만 바뀌면 코드 패키지를 재사용한다. Stage는 선택한 전체 Spec으로 새 세션을 실행한다.

별도 에이전트 서비스의 운영 배포는 필요하지 않다. 공통 Stage 플랫폼은 사전에 준비하며, 코드 업로드와 실행 준비 과정은 수행한다.

#### 시나리오 B · AI 엔지니어의 버전 비교

1. AI 엔지니어는 테스트 셋과 평가 기준을 정의한다. 비교할 두 버전을 선택한다.
2. AI 엔지니어는 Stage Runner에서 두 버전을 실행한다. 의도한 변경 외의 시험 조건은 같게 유지한다.
3. AI 엔지니어는 평가 결과와 실행 기록을 비교하고 개선할 내용을 개발자와 공유한다.

**완료 기준:** 같은 형상을 로컬과 Stage에서 실행한다. 입력·출력 매핑과 두 턴의 대화를 확인한다. 선택한 Spec 해시가 실행 기록과 일치하고 설정 변경이 실제 결과에 반영돼야 한다.

### 5.2 Phase1 · Builder와 plugin 협업 · 6주

**목표:** 기획자의 직접 플로우 편집과 개발자의 변경 검토를 연결한다.

개발 대상은 플로우 편집이 가능한 Agent Builder와 변경 비교를 제공하는 개발자 plugin이다. 형상 관리에 실험 작업본을 추가하고 Runner·평가 도구를 연결한다. 플랫폼은 Playground의 Git 작업을 처리한다.

#### 시나리오 A · 개발자의 평가 반복

1. **형상 동기화와 버전 관리:** 개발자는 에이전트 manifest를 선택한다. Plugin은 SDK와 같은 형식으로 정의·필요 소스·의존성을 가져온다. 이미 시험한 고정 형상도 재사용할 수 있다. 플랫폼은 새 기준 버전을 기록한다.
2. **평가 반복:** 개발자는 같은 테스트 셋과 품질 기준으로 평가한다. 결과와 실행 기록을 확인한다. 수정한 형상을 새 버전으로 동기화하고 재평가한다.

#### 시나리오 B · 기획자의 플로우 수정과 개선 제안

1. 기획자는 가져온 기준 형상에서 실험 작업본을 만든다. 최신 형상이 필요하면 개발자에게 plugin 동기화를 요청한다.
2. 기획자는 허용된 노드를 추가·삭제하고 연결·분기·설정을 수정한다. 개발자 기술 지원 없이 변경한 흐름을 실행한다. AI 엔지니어와 결과를 검토하고 실험 버전을 기록한다.
3. 기획자는 인계할 실험 버전을 선택한다. 플랫폼은 기준 형상·선정 형상·최종 변경점·구성 요소 참조·평가 근거를 변경 제안으로 내보낸다.
4. 개발자는 plugin에서 기준 형상·선정 형상·현재 로컬을 비교한다. 공통 Spec은 선택 적용하고 Python 코드로 작성한 흐름은 제안을 보고 반영한다. 서비스 시험 후 결정과 이유를 기록한다.

**완료 기준:** 기획자는 허용된 플로우를 직접 편집·실행·평가한다. 화면에서 수정한 Spec이 실제로 실행돼야 한다. 개발자는 인계한 변경을 실제 프로젝트에서 검토·시험한다. 기존 실험과 검토 이력은 유지한다.

Builder와 plugin은 노드·연결·분기 편집 권한과 변경 비교 계약을 확정한 뒤 개발한다. 초기에는 모의 응답을 사용하고 실행·평가 경로가 준비되면 연결한다. Phase0 시나리오는 5~6주에, Phase1 시나리오는 9~10주에 검증한다.

작업 범위와 의존성은 [WBS 상세](./agent-playground-wbs.md)를 따른다. 셀 색을 유지해 복사하려면 [Excel 표](./assets/agent-playground-wbs.xlsx)를 사용한다.

## 6. 성과 확인 지표

| 지표 | 확인 방법 |
| --- | --- |
| 에이전트 개선·평가 주기 소요 시간 | 개선 작업 시작부터 수정·재평가 후 결과 검토가 완료될 때까지 측정한다. |
| 에이전트 수정 후 품질 검증 소요 시간 | 수정본 제출부터 품질 기준의 통과 여부를 확인할 때까지 측정한다. 패키지 준비·실행·평가 대기를 포함한다. |
| 실험 변경 제안 검토 완료율 | 검토 기간이 지난 제안 중 개발자가 기한 내에 검토를 마치고 반영 여부와 이유를 기록한 비율이다. |

품질 검증 시간은 개선·평가 주기의 하위 지표다. 기존 방식과 유사한 개선 과제로 비교한다. 테스트 셋·평가 범위·품질 기준을 유지하고 실패·시간 초과·미완료도 함께 확인한다.

반영·부분 반영·미반영 모두 이유를 기록하면 검토 완료로 본다. 이 비율은 검토 응답성을 뜻한다. 결정 유형과 이유도 함께 확인한다. 검토 기간이 지나지 않은 제안은 별도로 확인한다.

Phase0에서 두 시간 지표의 기준값을, Phase1에서 협업 지표의 기준값을 수집한다. 검토 기간은 제안 공유 전에 정한다. 수치 목표는 기준값 확인 후 정한다. 상세 집계는 [성과 지표 측정 기준](./agent-playground-metrics-review.md)을 따른다.
