# Agent Playground 기획

> 작성일: 2026-10-07. 상태: 상위 기획 초안.
> 작성 기준: [ASD-STE100](https://www.asd-ste100.org/STE_faq.html)의 작성 원칙을 한국어에 적용했다. 공식 준수를 뜻하지 않는다.

## 1. 개요

### 추진 배경

개발자는 에이전트마다 시험 환경과 평가 절차를 구성한다. 기획자는 설정 변경과 시험을 개발자에게 요청한다. 개발자는 환경 구성과 시험 지원을 반복한다. 각 역할이 버전별 결과와 실패 원인을 같은 기준으로 확인하기 어렵다.

### 목적과 범위

**제작 방식이 달라도 같은 방식으로 시험·검증하고 산출물을 관리한다.** 기획자, AI 엔지니어, 개발자는 같은 Playground 형상과 평가 결과로 개선할 내용을 결정한다.

대상은 공통 실행 계약을 지원하는 에이전트다. 첫 SDK 언어는 Python이다. Playground는 정의·실행·평가·편집·변경사항 공유를 제공한다. 개발자는 기존 절차로 서비스를 통합하고 배포한다.

Builder는 허용된 구성 요소와 설정을 편집한다. 사용자 구현은 보존한다. 지원하지 않는 구조는 읽기 전용으로 표시한다. 개발자는 해당 코드를 실제 서비스 프로젝트에서 수정한다.

## 2. 타겟 사용자

| 사용자 | 주요 요구 | 역할 |
| --- | --- | --- |
| 서비스 기획자 | 개발자 지원을 기다리지 않고 기능과 설정을 실험한다. | 시험 사례와 품질 기준을 정의한다. 허용 범위에서 실험하고 결과를 검토한다. |
| AI 엔지니어 | 같은 테스트 셋으로 버전을 비교하고 실패 원인을 찾는다. | 평가 방법과 테스트 셋을 관리한다. 설정을 실험한다. 코드는 실제 서비스 프로젝트에서 수정한다. |
| 백엔드 개발자 | 시험 환경과 실행 연동의 반복 개발을 줄인다. | 실제 서비스 프로젝트와 실행 계약을 관리한다. 형상을 가져오고 제안한 변경사항을 검토·반영한다. |

세 역할은 반영할 변경사항을 함께 선정한다.

## 3. 목표와 기대효과

**시험 준비와 협업 대기를 줄여 품질 개선에 필요한 실행·평가·검토를 빠르게 이어간다.**

| 목표 | 기대효과 | 성과 확인 지표 |
| --- | --- | --- |
| 제작 방식에 관계없이 공통 경로로 시험·검증한다. | 개발자는 공통 시험 환경을 사용한다. 서비스 배포 없이 수정본을 시험해 품질 검증 시간을 줄인다. | 에이전트 수정 후 품질 검증 소요 시간 |
| 평가 근거로 개선·재평가를 반복한다. | AI 엔지니어와 개발자는 같은 기준으로 변경 효과를 비교한다. 실행 기록으로 실패 원인을 찾아 개선·재평가 시간을 줄인다. | 에이전트 개선·평가 주기 소요 시간 |
| 기획자의 실험을 개발자의 개선 결정으로 연결한다. | 기획자는 허용 범위에서 직접 실험한다. 개발자는 변경사항과 평가 근거로 반영 여부를 결정한다. 실험 요청과 결과 전달의 대기를 줄인다. | 실험 변경 제안 검토 완료율 |

개선 효과는 사전에 정한 품질 기준으로 확인한다.

## 4. 컴포넌트 구성

| 컴포넌트 | 책임 |
| --- | --- |
| Agent Spec·Python SDK | 공통 정의와 실행 계약을 제공한다. 사용자 구현과 편집 가능한 설정을 연결한다. |
| Playground 형상·빌드 관리 | KPAP의 별도 GitHub 저장소에서 기준 형상과 실험 이력을 관리한다. 실행 패키지를 고정한다. |
| Stage Runner | 선택한 버전을 격리 환경에서 실행한다. 세션과 시험 환경을 관리한다. |
| 평가 도구 | Langfuse로 실행 기록과 평가 결과를 버전에 연결한다. 고정 테스트 셋과 시험 조건으로 버전을 비교한다. |
| Agent Builder | 에이전트 형상을 표시한다. 허용된 구성 요소와 설정을 편집하고 시험 결과를 보여준다. |
| 개발자 plugin | 서비스 형상을 Playground로 가져온다. 실험 변경사항과 평가 근거를 실제 프로젝트의 로컬에서 보여준다. |

이 문서의 형상 동기화는 plugin으로 현재 에이전트 형상을 Playground에 가져오는 작업이다. 실제 서비스 형상과 Playground 형상은 별도로 관리한다.

상세 계약은 [Python SDK 스펙](./agent-sdk-spec.md)과 [산출물·형상관리 문서](./agent-playground-collaboration-lifecycle.md)를 따른다. [기존 Runner 설계](./agent-stage-runner-design.md)의 Java 실행 계약은 Python SDK 기준으로 조정한다.

## 5. 단계별 로드맵

각 Phase의 예상 개발 기간은 6주다. Phase0를 1~6주, Phase1을 5~10주에 배치한 예시다. 공통 계약을 확정한 뒤 두 단계의 개발을 일부 병행한다. 실제 일정은 투입 인원과 파일럿 결과로 정한다.

### 5.1 Phase0 · SDK 실행과 평가 · 6주

**목표:** SDK 에이전트를 서비스 배포 없이 Stage Runner에서 실행·평가한다.

개발 대상은 Agent Spec·Python SDK, Playground 형상·빌드 관리, Stage Runner, 평가 도구다.

#### 시나리오 A · 개발자의 SDK 에이전트 시험

1. 개발자는 실제 서비스 프로젝트에서 SDK로 에이전트를 구현한다.
2. 개발자는 SDK의 Stage 실행 기능으로 정의·소스·의존성을 전달한다. 플랫폼은 형상을 저장하고 실행 패키지와 환경을 준비한다.
3. 개발자는 준비된 Stage Runner에서 메시지와 후속 대화를 시험한다. 별도 서비스 배포는 필요하지 않다.
4. 개발자는 실행 기록을 확인하고 코드를 수정한다. 다시 실행을 요청하면 플랫폼은 새 버전으로 새 세션을 만든다.

#### 시나리오 B · AI 엔지니어의 버전 비교

1. AI 엔지니어는 테스트 셋과 평가 기준을 정의한다. 비교할 두 버전을 선택한다.
2. AI 엔지니어는 Stage Runner에서 두 버전을 실행한다. 의도한 변경 외의 시험 조건은 같게 유지한다.
3. AI 엔지니어는 평가 결과와 실행 기록을 비교하고 개선할 내용을 개발자와 공유한다.

**완료 기준:** 개발자는 SDK 작성부터 Stage 실행까지 수행할 수 있다. AI 엔지니어는 버전을 비교하고 실패를 정확한 버전의 기록에서 확인할 수 있다.

### 5.2 Phase1 · Builder와 plugin 협업 · 6주

**목표:** 개발자의 평가 반복과 기획자의 기능 실험을 실제 프로젝트의 개선 검토로 연결한다.

개발 대상은 Agent Builder와 개발자 plugin이다. 형상 관리에 실험 작업본을 추가하고 Runner·평가 도구를 Builder에 연결한다. 플랫폼은 Playground의 Git 작업을 처리한다.

#### 시나리오 A · 개발자의 평가 반복

1. **형상 동기화와 버전 관리:** 개발자는 plugin으로 현재 형상을 가져온다. 플랫폼은 새 기준 버전을 기록하고 기존 실험 이력을 유지한다.
2. **평가 반복:** 개발자는 같은 테스트 셋과 품질 기준으로 평가한다. 결과와 실행 기록을 확인한다. 수정한 형상을 새 버전으로 동기화하고 재평가한다.

#### 시나리오 B · 기획자의 기능 추가 실험과 개선 제안

1. 기획자는 개발자에게 현재 형상의 동기화를 요청한다. 개발자는 plugin으로 해당 형상을 가져온다.
2. 기획자는 Builder의 허용 범위에서 기능을 추가하거나 설정을 변경한다. AI 엔지니어와 결과를 검증한다. 플랫폼은 실험 버전을 기록한다.
3. 기획자는 선정한 실험의 변경사항과 평가 근거를 공유한다. 개발자에게 변경사항 확인을 요청한다.
4. 개발자는 plugin에서 실험 변경사항과 실제 프로젝트의 현재 형상을 비교한다. 주요 변경사항과 충돌을 확인하고 적용 여부를 검토한다.

**완료 기준:** 개발자는 버전별 평가를 반복할 수 있다. 기획자는 변경사항을 전달하고 검토 결과를 확인할 수 있다. 플랫폼은 새 동기화 후에도 기존 실험과 평가 이력을 유지한다.

### 5.3 WBS 일정

🟦는 Phase0, 🟩는 Phase1이다. 주차는 착수일부터 계산한다.

| 컴포넌트 | 1~2주 | 3~4주 | 5~6주 | 7~8주 | 9~10주 |
| --- | --- | --- | --- | --- | --- |
| Agent Spec·Python SDK | 🟦 계약·기본 구현 | 🟦 내보내기·실행 연동 | 🟦 Stage 검증 / 🟩 호환 연동 | 🟩 연동 보완 | 🟩 통합 검증 |
| Playground 형상·빌드 관리 | 🟦 저장소·형상 등록 | 🟦 패키지·환경 준비 | 🟦 실행 검증 / 🟩 실험 작업본 | 🟩 변경 이력·공유 | 🟩 통합 검증 |
| Stage Runner | 🟦 Python 실행 | 🟦 세션·격리·환경 연결 | 🟦 SDK 시험 검증 | 🟩 Builder 시험 연결 | 🟩 통합 검증 |
| 평가 도구 | 🟦 평가 계약·테스트 셋 | 🟦 기록·평가 연동 | 🟦 버전 비교 검증 | 🟩 공동 결과·평가 근거 | 🟩 통합 검증 |
| Agent Builder | — | — | 🟩 import·설정 편집 | 🟩 시험·결과 화면 | 🟩 기획자 시나리오 검증 |
| 개발자 plugin | — | — | 🟩 import·파일 대응 | 🟩 변경점·선택 반영 | 🟩 개발자 시나리오 검증 |

Builder와 plugin은 공통 정의·수정 권한·가져오기 계약을 확정한 뒤 개발한다. 초기에는 모의 응답을 사용하고 실행·평가 경로가 준비되면 연결한다. Phase0 시나리오는 5~6주에, Phase1 시나리오는 9~10주에 검증한다.

작업 범위와 의존성은 [WBS 상세](./agent-playground-wbs.md)를 따른다. 셀 색을 유지해 복사하려면 [Excel 표](./assets/agent-playground-wbs.xlsx)를 사용한다.

## 6. 성과 확인 지표

| 지표 | 확인 방법 |
| --- | --- |
| 에이전트 개선·평가 주기 소요 시간 | 개선 작업 시작부터 수정·재평가 후 결과 검토가 완료될 때까지 측정한다. |
| 에이전트 수정 후 품질 검증 소요 시간 | 수정본 제출부터 품질 기준의 통과 여부를 확인할 때까지 측정한다. 패키지 준비·실행·평가 대기를 포함한다. |
| 실험 변경 제안 검토 완료율 | 검토 기간이 지난 제안 중 개발자가 기한 내에 검토를 마치고 반영 여부와 이유를 기록한 비율이다. |

품질 검증 시간은 개선·평가 주기에 포함된다. 같은 테스트 셋과 유사한 실행 조건에서 비교한다. 실패·시간 초과·미완료도 함께 확인한다.

반영·부분 반영·미반영 모두 이유를 기록하면 검토 완료로 본다. 검토 기간이 지나지 않은 제안은 별도로 확인한다.

Phase0에서 두 시간 지표의 기준값을, Phase1에서 협업 지표의 기준값을 수집한다. 검토 기간은 제안 공유 전에 정한다. 수치 목표는 기준값 확인 후 정한다. 상세 집계는 [성과 지표 측정 기준](./agent-playground-metrics-review.md)을 따른다.
