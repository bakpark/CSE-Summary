# Agentic Platform의 사내 가치와 확장 전략

문서 상태: 전략 검토 초안

작성 기준일: 2026-09-28

## 1. 핵심 주장

Agentic Platform은 Lobby나 n8n을 대체하는 세 번째 Agent Builder가 아니다.

> **Lobby·n8n·CCAB 등에서 시작된 Agent와 Workflow가 더 높은 복잡도, 재사용성, 위험도를 가질 때 이를 검증하고 안전하게 운영하며 여러 채널에 공급하는 공통 실행 기반이다.**

사내에서는 개인의 업무 방식을 회사가 운영할 수 있는 자산으로 전환한다. 장기적으로는 여기서 확보한 제작·검증·권한·운영 역량을 결제·혜택·송금 영역의 대고객 Agent로 확장한다.

## 2. 사내에 제공하는 가치

### 2.1 개인의 업무 방식을 회사의 자산으로 전환

반복 업무의 절차와 판단 기준은 개인의 경험, 문서, Prompt, Lobby Agent, n8n Workflow 등에 흩어져 있다. 플랫폼은 이를 다음 요소가 포함된 운영 가능한 Agent로 전환한다.

- 업무 목표와 완료 조건
- 입력과 결과 형식
- 업무 절차와 판단 기준
- 사용할 지식과 도구
- 접근 가능한 데이터와 권한
- 사람의 확인이 필요한 조건
- 실제 사례와 품질 기준
- 배포 버전과 실행 기록

가치는 Agent를 많이 만드는 데 있지 않다. **사람이 알고 있던 업무 방식을 조직이 반복 실행하고 검증·개선할 수 있게 만드는 것**에 있다.

### 2.2 비개발자와 개발환경 사이의 간극 해소

CCAB는 비개발자가 자연어로 코드형 Agent를 만드는 과정을 지원한다. 그러나 생성된 코드를 실행하고 검증하려면 저장소, 개발환경, 의존성 설치와 Tool 연동이 필요하다.

Agent Stage Runner는 다음을 플랫폼 환경에서 대신한다.

- GitHub 계정과 로컬 개발환경
- 코드와 의존성 설치
- 실행과 오류 확인
- Tool 연결 시험
- 실제 사례 기반 테스트
- 배포 가능한 결과물 생성

따라서 플랫폼은 자연어 작성 화면을 하나 더 제공하는 것이 아니라, **비개발자가 정의한 업무를 운영 가능한 수준까지 끌어올리는 환경**을 제공한다.

### 2.3 안전한 권한과 책임 구조

Agent가 사내 Tool을 직접 호출하는 것만으로는 다음을 일관되게 관리하기 어렵다.

- 누구의 권한으로 실행했는가
- 어떤 데이터와 기능까지 접근할 수 있는가
- 쓰기 작업 전에 승인을 받았는가
- 동일 작업이 중복 실행되지 않았는가
- 어떤 Agent 버전이 결과를 만들었는가
- 문제가 발생했을 때 즉시 중지할 수 있는가

플랫폼은 이러한 기준을 Prompt가 아니라 실행 환경에서 강제한다. 이는 향후 고객 데이터와 결제·송금 시스템을 다루기 위한 선행 역량이기도 하다.

### 2.4 채널에 종속되지 않는 공급

Agent의 업무 정의와 실행 채널을 분리하면 하나의 검증된 Agent를 다음 환경에 공급할 수 있다.

- KPAP(Web)
- Claude Desktop
- Slack
- 정기 실행과 시스템 Event
- 향후 고객 App·Web·상담 채널

회사가 소유해야 하는 핵심 자산은 특정 화면이나 Prompt가 아니라 **검증된 업무 정의, 권한 정책과 실행 이력**이다.

## 3. Lobby·n8n·CCAB와의 역할 분담

기존 도구의 한계를 과장하기보다 각 도구가 가장 잘하는 영역을 인정하고, 필요한 경우에만 플랫폼의 관리 수준으로 올리는 것이 적절하다.

| 업무 유형 | 기본 선택 |
|---|---|
| 사내 지식을 찾아 답변하는 간단한 Agent | Lobby |
| 순서와 분기가 미리 정해진 자동화 | n8n |
| 코드, 복잡한 판단, 반복 테스트가 필요한 Agent | CCAB + Agent Stage Runner |
| 여러 채널에서 반복 운영해야 하는 Agent | Agentic Platform 실행 환경 |
| 결제·송금 등 정확한 거래 처리 | 기존 도메인 시스템 |

### 3.1 Lobby와의 공존

Lobby는 지식과 MCP를 조합해 Web에서 빠르게 Agent를 만들고 사용하는 데 적합하다. 지식 검색, 단순 질의응답, 제공된 Tool을 사용하는 제한된 업무는 Lobby에 남겨두는 편이 효율적이다.

다음 조건이 생기면 Agentic Platform에서 관리하는 대상으로 올릴 수 있다.

- 여러 채널에서 사용해야 한다.
- 코드나 별도 의존성이 필요하다.
- 실제 사례를 반복 시험해야 한다.
- 버전, 권한, 승인과 실행 이력이 중요하다.
- 높은 가용성이나 실패 복구가 필요하다.

Agentic Platform은 Lobby의 상위 제품이 아니라, **Lobby에서 시작된 업무가 더 강한 운영 기준을 필요로 할 때 선택하는 다음 단계**다.

### 3.2 n8n과의 공존

n8n은 Trigger, 일정, 분기와 시스템 Action이 명확한 업무에 적합하다. 이를 Agentic Platform으로 다시 만들 필요는 없다.

```text
업무 Event 또는 일정
        ↓
       n8n
        ↓
판단이 필요한 구간에서 Agent 호출
        ↓
Agentic Platform
        ↓
검증된 결과를 n8n에 반환
        ↓
후속 시스템 처리
```

역할은 다음과 같이 나눈다.

- **n8n**: 언제 시작하고 어떤 순서로 진행할지 관리
- **Agent**: 비정형 정보를 조사하고 상황에 따라 판단
- **Agentic Platform**: Agent의 버전, 권한, 실행, 평가와 기록 관리
- **업무 시스템**: 실제 데이터와 거래의 최종 정합성 보장

플랫폼이 일반적인 Workflow 기능을 무분별하게 확장하면 n8n과 중복된다. 반대로 n8n 안에 모든 Agent 코드와 Prompt를 넣으면 검증과 운영 기준이 Workflow별로 흩어진다. 따라서 **n8n은 업무 흐름을 연결하고, 플랫폼은 판단 가능한 Agent를 운영한다**는 경계를 유지한다.

### 3.3 CCAB와의 공존

CCAB는 Agent를 만드는 사용자 경험을 담당한다. Agentic Platform은 CCAB가 생성한 결과물을 실행·검증·배포하는 환경을 담당한다.

```text
CCAB                    Agentic Platform
Agent 초안 생성    →    원격 실행·검증
업무 절차와 코드   →    버전·권한·평가 관리
오류 수정          ←    실행 결과와 오류 반환
배포 요청          →    검증된 버전 활성화
```

플랫폼이 별도 Builder 화면을 먼저 만들기보다, 기존 CCAB의 제작 경험을 운영 환경과 연결하는 것이 우선이다.

## 4. 선택적 관리 수준

모든 Agent를 플랫폼에 강제로 등록하면 플랫폼이 새로운 병목이 된다. 복잡도, 위험도와 재사용 범위에 따라 필요한 관리 수준을 선택한다.

### 1단계: 도구 안에서 사용

Lobby나 n8n에서 만든 단순 Agent와 Workflow를 그대로 사용한다. 실패 영향이 작고 사용 범위가 제한적이며 다른 채널에서 재사용하지 않는 경우다.

### 2단계: 조직 내 공유

여러 사람이 반복 사용하기 시작하면 담당자, 목적, 사용 Tool과 버전을 등록한다.

### 3단계: 관리형 Agent

다음 조건에서는 Stage Runner의 검증과 플랫폼 실행 환경을 사용한다.

- 코드와 별도 의존성이 있다.
- 쓰기 작업을 수행한다.
- 여러 채널에서 사용한다.
- 운영 품질과 실행 이력이 중요하다.
- 승인과 세부 권한이 필요하다.

### 4단계: 대고객 Agent

고객이 사용하거나 고객 데이터와 거래를 다루는 Agent에는 별도의 고객용 실행 환경과 강화된 검증·보안 기준을 적용한다.

이 구조에서 Lobby와 n8n은 없어지지 않는다. 두 도구는 Agent 발굴과 간단한 자동화의 주요 진입점으로 계속 기능한다.

## 5. 출구전략

플랫폼이 전체 제품으로 성장하지 못하더라도 기존 도구로 돌아갈 수 있고, 개발한 기능이 공통 자산으로 남도록 설계한다.

### 5.1 구성요소를 독립적으로 사용

다음 기능을 하나의 거대한 제품에 묶지 않고 독립적으로 사용할 수 있게 한다.

- Agent Stage Runner
- Tool Gateway
- 에이전트 버전과 배포 관리
- 실행 환경
- 평가와 실행 기록
- 채널 연결

전체 플랫폼에 대한 수요가 충분하지 않더라도 Stage Runner와 Tool Gateway는 CCAB·Lobby·n8n을 위한 공통 서비스로 남길 수 있다.

### 5.2 특정 Builder와 모델에 종속되지 않음

Agent는 Claude나 CCAB 전용 설정이 아니라 다음 내용을 가진 일반적인 배포 단위로 보관한다.

- 업무 정의
- Source와 의존성
- Tool 목록과 버전
- 권한 정책
- 테스트 사례와 평가 결과
- 실행 설정

이를 통해 Builder나 모델이 변경되어도 업무 정의와 검증 자산을 유지한다.

### 5.3 기존 도구의 발전을 수용

Lobby가 향후 코드 실행, 평가와 버전 관리까지 제공한다면 별도 Builder를 만들 필요가 없다. Lobby가 Stage Runner와 공통 관리 기능을 사용하도록 통합할 수 있다.

n8n이 Agent 실행 관리 기능을 충분히 제공한다면 Workflow 실행은 n8n에 남기고 Tool Gateway, 권한과 평가 기능만 공통으로 제공할 수 있다.

즉, 출구전략은 기존 도구를 교체하는 것이 아니라 **플랫폼 구성요소를 기존 도구에서도 사용할 수 있는 공통 서비스로 남기는 것**이다.

### 5.4 확장 중단 기준

다음 질문에 답하지 못하면 별도 플랫폼 확장을 보류한다.

- Lobby나 n8n보다 복잡한 업무 사례가 실제로 존재하는가
- Stage Runner가 Agent 제작과 검증 시간을 줄이는가
- 여러 채널에서 재사용되는 Agent가 발생하는가
- 권한·승인·감사 기능에 실질적인 수요가 있는가
- 운영 성공률과 사람의 개입 시간이 개선되는가

확장을 중단하더라도 Tool Gateway, CCAB 개선과 원격 시험 환경은 독립적인 성과로 남는다.

## 6. 대고객 Agent로의 확장

사내용 Agent와 대고객 Agent는 제작·검증·관리 기반을 공유할 수 있다. 그러나 사용자와 데이터, 위험 수준이 다르므로 실행 환경과 권한 경계는 분리해야 한다.

### 6.1 함께 사용할 수 있는 기반

- CCAB를 포함한 Agent 제작 방식
- Agent Stage Runner
- 코드·의존성·배포 버전 관리
- Tool Gateway의 API 계약
- 실제 사례 기반 테스트
- 실행 추적과 품질 평가
- 채널 연결 방식
- 중지와 되돌리기

### 6.2 분리해야 하는 영역

| 구분 | 사내용 Agent | 대고객 Agent |
|---|---|---|
| 사용자 | 임직원 | 고객·가맹점·파트너 |
| 권한 | 사내 계정과 직무 권한 | 본인 인증과 서비스 자격 |
| 데이터 | 사내 문서·업무 데이터 | 개인정보·금융정보·거래정보 |
| 실행 환경 | 업무 생산성 중심 | 고객 서비스 수준과 장애 격리 중심 |
| 승인 | 담당자·관리자 확인 | 고객의 명시적 확인과 추가 인증 |
| 위험 기준 | 업무 오류·정보 노출 | 금전 손실·오거래·규제 위반 |
| 가용성 | 사내 업무 기준 | 대고객 서비스 기준 |

```text
                 공통 제작·관리 기반
       CCAB · Stage Runner · Agent 관리 · 평가
                          │
           ┌──────────────┴──────────────┐
           ▼                             ▼
    사내용 실행 환경                대고객 실행 환경
    KPAP · Claude · Slack           고객 App · Web · 상담
    사내 계정·업무 권한              본인 인증·거래 권한
           │                             │
           └──────── Tool Gateway ───────┘
                         │
          업무 API · 결제 · 혜택 · 송금 API
```

### 6.3 확장 순서

1. **조회·안내 Agent**
   - 결제 내역 설명
   - 받을 수 있는 혜택 탐색
   - 송금 상태와 실패 원인 안내
   - 필요한 서류와 절차 안내

2. **업무 보조 Agent**
   - 고객 의도를 구조화해 기존 서비스 화면으로 연결
   - 신청서 초안 작성
   - 문의 분류와 상담원 인계
   - 처리 상태 추적과 알림

3. **사람의 확인을 포함한 실행**
   - 실행 내용과 영향을 고객에게 명확히 제시
   - 고객 확인과 추가 인증 이후 API 호출
   - 결과 확인과 실패 복구

4. **복합 서비스 Agent**
   - 여러 서비스와 시스템을 연결해 고객 목표 처리
   - 결제·송금의 최종 판단과 거래 정합성은 기존 도메인 시스템이 담당

대고객 Agent에서 모델은 고객 의도를 이해하고 필요한 절차를 조율한다. 금액, 수취인, 한도, 수수료, 중복 실행 여부와 실제 자금 이동은 기존 결제·송금 시스템이 결정하고 보장한다.

## 7. 사내 적용과 대고객 확장을 연결하는 논리

사내 업무 생산성은 최종 목적에 한정되지 않는다. **안전한 Agent 운영 능력을 학습하는 첫 번째 적용 영역**이다.

사내 Agent를 운영하면서 다음 역량을 검증할 수 있다.

- 비개발자가 Agent를 만들고 수정하는 방법
- 코드를 격리 실행하고 검증하는 방법
- Tool 권한을 제한하는 방법
- 사람의 확인을 실행 중간에 받는 방법
- Agent의 품질과 실패를 측정하는 방법
- 여러 채널에 동일한 Agent를 제공하는 방법
- 문제 있는 버전을 중지하고 되돌리는 방법

이 역량은 대고객 Agent에도 필요하다. 고객용 환경에서는 인증, 보안, 가용성과 거래 안전 기준을 추가로 강화한다.

> **Agentic Platform은 사내 생산성 Agent에서 시작해, 회사의 업무와 서비스 절차를 검증된 Agent로 만들고 임직원과 고객이 있는 모든 채널에 안전하게 제공하는 공통 실행 기반으로 발전한다.**

## 8. 최종 포지셔닝

상위 보고에서는 다음 세 문장으로 설명할 수 있다.

> Agentic Platform은 Lobby나 n8n을 대체하는 세 번째 Builder가 아니다.
>
> 기존 도구에서 시작된 Agent와 Workflow가 더 높은 재사용성·복잡도·위험도를 가질 때 검증하고 운영하는 공통 기반이다.
>
> 사내 Agent를 통해 확보한 제작·검증·권한·운영 역량은 향후 결제·혜택·송금 영역의 대고객 Agent로 확장된다.
