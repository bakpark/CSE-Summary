# Agent Playground Agent Builder MVP 설계

> 작성일: 2026-10-05. 재검토일: 2026-10-06. 상태: 구현 기준.
> 작성 기준: ASD-STE100의 원칙을 한국어에 적용했다. 공식 준수를 뜻하지 않는다.
> 관련 문서: [Agent Definition](agent-definition-design.md), [Stage Runner](agent-stage-runner-design.md).
> 주 편집기: [프로토타입](https://github.com/bakpark/CSE-Summary/tree/master/AI%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8/agent-builder/prototype).

## 1. 목적과 책임

**Builder는 자연어와 캔버스로 에이전트를 편집하고 Java 그래프 코드를 생성한다.**
Definition은 저장과 버전을 담당한다.
Jenkins Agent CI는 고정 코드를 컴파일하고 JAR를 사내 Nexus에 등록한다.
Runner는 등록한 JAR로 시험을 담당한다.
SDK는 실행 의미와 대화 상태를 담당한다.
Builder는 사용자 코드를 실행하지 않는다.

### 연계 세부 계약의 확정 필요

컴포넌트의 책임과 연계 흐름은 이 문서를 따른다.
세부 계약은 구현 전에 세 문서에서 같은 기준으로 확정해야 한다.

- 연계 API의 요청·응답 필드와 오류 코드
- SDK 인터페이스의 실제 타입과 메서드 서명
- 모델·도구 ID와 환경 연결의 매핑 규칙

현재 예시와 설명은 최종 API 명세가 아니다.
이 항목은 후속 확정 사항이며 MVP 기능 범위를 추가하지 않는다.

## 2. 재사용과 추가 범위

| 구분 | 기능 |
| --- | --- |
| 재사용 | Flowise 캔버스, 노드 설정, 자연어 편집, 변경안 적용·취소, 작업 기록 |
| 추가 | Java 메서드 본문 편집, 그래프 코드 생성, 서버 저장, 시험 도구 선택, Agent CI 상태 표시와 Runner 테스트 연결 |
| 축소 | 전체 코드 편집, 입출력 매핑 편집, 단독 Flowise JSON 가져오기·내보내기 |

프로토타입은 현재 JavaScript Function과 브라우저 저장을 사용한다.
MVP는 Java 본문 편집과 서버 저장으로 바꾼다.
기존 자연어 연결 도구는 첫 출력만 선택한다.
MVP는 Condition의 true·false 출력 선택을 추가한다.
Flowise 원본 실행 서버는 설치하지 않는다.

## 3. 사용자 절차와 화면

1. Builder 대화에 업무와 변경 요청을 입력하십시오.
2. 변경 요약을 확인하십시오.
3. 변경안을 적용하거나 취소하십시오.
4. 필요한 노드 설정과 코드 본문을 직접 편집하십시오.
5. 편집본을 저장하십시오.
6. 해당 저장본의 CI 빌드·Registry 등록 결과를 확인하십시오.
7. 라이브러리가 준비되면 `테스트 시작`을 누르십시오.
8. 별도 테스트 대화에서 결과를 확인하십시오.
9. 수정 후 저장하고 새 라이브러리가 준비되면 `수정본 테스트`를 누르십시오.

Builder 대화는 제작 요청을 처리한다. 테스트 대화는 에이전트를 호출한다.
검토 패널은 노드·연결 변경 요약과 코드 본문의 전후 내용을 표시한다.
적용 전의 변경안은 저장과 시험에 포함하지 않는다.
UI는 변경 적용과 서버 저장 완료를 구분한다.
UI는 저장 중·저장 완료·저장 실패·변경 있음을 표시한다.
미저장 변경, 저장 중, 해당 저장본의 CI 미완료·실패 상태에서는 새 버전 테스트를 막는다.
저장 완료, 라이브러리 준비 완료, Runner 준비 완료는 다른 상태로 표시한다.
기존 시험 세션은 새 빌드 동안 유지한다. CI 성공 후에도 현재 세션은 유지한다. 사용자가 수정본 테스트를 눌렀을 때 새 JAR의 빈 세션으로 전환한다.
미완성 그래프는 저장할 수 있다. 저장 후 빌드 준비의 그래프 검사에서 오류를 표시하고, 생성 가능한 코드가 없으면 CI 컴파일·등록을 진행하지 않는다.

화면의 변경 순번은 자연어 변경안의 기준을 확인한다.
서버의 저장 순번은 저장 충돌을 확인한다.
편집본 다시 불러오기·노드 삭제·새 플로우 적용도 화면 변경 순번을 증가시킨다.
기준이 오래된 변경안은 적용하지 않는다.
사용자는 최신 편집본으로 다시 요청한다.

## 4. 편집과 코드 생성

### 노드 범위

| 노드 | 설정·동작 |
| --- | --- |
| Start | 현재 메시지를 request로 받는다. 하나만 허용한다. |
| LLM | 모델과 프롬프트로 단일 LLM 호출을 수행한다. |
| Agent | 모델·프롬프트·허용 조회/모킹 도구를 사용한다. SDK가 도구 반복을 제한한다. |
| Function | 고정 Java 메서드의 본문만 편집한다. 입력 Map을 읽고 결과 Map을 반환한다. |
| Condition | 직전 결과 필드와 값의 동등 비교로 true·false 경로를 선택한다. |
| Reply | 최종 답변을 반환한다. 다음 연결을 갖지 않는다. |

입출력과 대화 상태는 Definition의 SDK 계약을 따른다.
LLM 출력은 기본 텍스트다. 전체 JSON Schema 편집 기능은 추가하지 않는다.
Agent의 도구 입력·결과는 기존 시험 도구 계약을 사용한다.
코드 노드 본문이 JSON 값을 해석해 조건 비교용 필드를 만들 수 있다.
일반 노드는 다음 노드 하나만 연결한다.
Condition은 두 출력 포트를 연결한다.
순환과 병렬 연결은 지원하지 않는다.

### 생성과 CI 전달 절차

1. 사용자는 그래프와 코드 노드 본문을 서버에 저장한다.
2. 저장 완료와 빌드 요청을 연결한다. 플랫폼은 저장 순번과 요청 ID로 해당 저장본을 읽는다.
3. Builder 백엔드는 그래프의 연결과 상태 참조를 검사한다.
4. Builder 백엔드는 Java 그래프 구성 코드와 진단 위치 매핑을 생성한다.
5. Definition은 저장 순번을 재검사하고 원본·생성 코드를 버전으로 고정한다.
6. Jenkins Agent CI는 고정 버전과 고정 SDK로 컴파일·검증하고 Agent JAR를 사내 Nexus에 등록한다.
7. 성공한 buildId·버전 ID·artifactRef·체크섬·SDK 버전을 플랫폼에 기록한다.
8. Runner는 선택한 버전의 등록 JAR를 받아 검증한 뒤 세션에서 실행한다.

코드 저장 성공을 빌드 성공으로 표시하지 않는다. 빌드·등록 실패 시 이전 시험 버전을 성공한 새 버전처럼 표시하지 않는다. 늦게 도착한 이전 빌드 응답이 최신 편집본의 상태를 덮어쓰지 않는다.

Builder는 브라우저에서 받은 생성 코드를 신뢰하지 않는다.
Builder 백엔드의 생성 결과만 고정한다.
미완성 그래프, 끊긴 포트, 없는 코드 파일, Reply에 도달하지 않는 경로를 거부한다.
Java 본문의 문법과 SDK API 적합성 검사는 Agent CI가 수행한다.

노드 ID는 소스 파일·생성 클래스와 안정적으로 연결한다.
코드 노드 본문은 Java 파일 하나에만 보관한다.
그래프에는 파일 경로만 둔다.
그래프 생성은 기존 코드 노드 파일을 덮어쓰지 않는다.
노드 삭제를 적용하면 해당 코드 파일도 제거한다.
변경 검토에서 삭제되는 노드를 표시한다.

모델이 생성한 코드도 메서드 본문만 받는다.
백엔드는 고정 클래스·메서드 틀에 본문을 삽입한다.
입력·결과 예제는 SDK 계약의 기본 request와 output을 사용한다.
직접 편집은 메서드 본문만 허용한다.
자연어 편집도 같은 범위를 따른다.
생성된 클래스·진입점·그래프 코드는 편집할 수 없다.
Builder는 Java 코드를 캔버스로 역변환하지 않는다.

## 5. 실패와 접근 제한

저장·생성·컴파일 오류는 해당 노드 또는 코드 본문과 연결한다.
CI 컴파일 오류는 고정 버전의 파일·노드·본문 시작 행 매핑으로 보정한다. Runner의 JAR 로딩·open·invoke 오류는 시험 오류로 구분한다.
원인을 특정할 수 없으면 그래프 준비 오류로 표시한다.
실패를 다른 버전의 성공으로 대체하지 않는다.

Builder API는 소유자·허용 모델·도구를 확인한다.
자격증명은 서버 환경 연결에만 둔다.
파일과 본문 크기는 제한한다.
그래프 생성·버전 고정은 화면 미저장 상태를 기준으로 실행하지 않는다.
UI는 현재 시험 버전과 편집본의 차이를 표시한다.
자연어 요청은 6,000자, 모델 응답 반복은 10회로 제한한다.
전체 요청 시간 제한은 기본 120초다.
브라우저 저장은 복구 보조로만 사용한다. 시험 기준은 서버 저장본이다.

## 6. CI/CD와 구현 순서

1. SDK의 노드·진입점 계약을 확정한다.
2. 코드 노드 UI와 자연어 생성 규칙을 Java 본문으로 바꾼다.
3. 그래프 검사와 Java 생성 템플릿을 구현한다.
4. Definition 저장·버전 고정과 연결한다.
5. 저장 → Agent CI → Registry 등록 상태와 컴파일 오류를 연결한다.
6. Runner의 등록 JAR 시험·로딩 오류 표시를 연결한다.

CI는 타입 검사, 생성 코드·연결 검사 테스트, 프런트엔드 빌드를 수행한다.
SDK와 함께 예제 코드를 컴파일·실행해 생성 계약을 확인한다.
Stage 배포는 담당자가 기존 배포 도구로 수행한다.
Agentflow 패키지는 현재 프로토타입의 버전으로 고정한다.
패키지·템플릿 변경 시 기존 편집본을 조용히 변환하지 않는다.
호환되지 않는 편집본은 오류를 표시한다.
편집 저장은 Agent CI를 호출하지만 플랫폼 자체를 배포하거나 런타임 이미지를 다시 빌드하지 않는다. 사용자 빌드 스크립트는 받지 않고 플랫폼이 고정한 파이프라인을 사용한다.

## 7. 완료 기준과 제외 범위

- 자연어 변경안을 적용·취소하고 직접 편집할 수 있다.
- 미완성 편집본을 저장하고 다시 열 수 있다.
- 그래프 변경 후 코드 노드 본문이 유지된다.
- true·false 분기가 생성 코드와 일치한다.
- 오래된 변경안과 저장 충돌을 거부한다.
- 코드 오류를 고친 뒤 새 버전에서 시험할 수 있다.

공동 편집, 코드 역변환, JSON 파일 이동, 전체 입출력 스키마 편집은 제외한다.
범용 Flowise 호환, 외부 라이브러리, Git 자동화, 자동 회귀 검증도 제외한다.
프로토타입의 전체 입력·출력 스키마 설정은 MVP 화면에서 숨긴다.
새 노드 종류나 범용 매핑 기능이 필요하면 파일럿 사례로 먼저 확인한다.
프로토타입 재사용 가능성은 소스로 확인했다. Java 생성·Runner 연결은 아직 구현하지 않았다.
