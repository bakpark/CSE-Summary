# 사내 에이전트 빌더·런타임 플랫폼 제안

작성 기준일: 2026-09-23

## 결론

사내 플랫폼을 **“비개발자가 자연어로 에이전트를 만드는 도구”**로 정의하면 Claude의 Skill·MCP·예약 실행과 중복된다. 가장 방어력 있는 정의는 다음과 같다.

> **현업이 업무 규칙을 정의하면, 이를 검증·승인된 실행 가능한 프로세스로 바꾸고 회사의 권한·상태·SLA·감사 정책 아래 반복 운영하는 업무 실행 플랫폼**

Claude Desktop은 직원이 일을 요청하고 결과를 받는 **대화형 프런트도어**로 유지한다. 사내 플랫폼은 Claude가 MCP로 호출하는 **업무 실행 및 통제 계층**이 된다.

이 플랫폼이 해결해야 할 핵심 문제는 “AI에게 일을 시킬 수 없음”이 아니다. 이미 가능하다. 해결할 문제는 다음이다.

> **한 번 잘 수행한 AI 업무를 다른 사람도 같은 품질과 통제 수준으로 반복 실행할 수 없고, 장시간·다단계 업무를 회사가 운영 가능한 형태로 맡기기 어렵다.**

## 시장 리서치에서 확인한 방향

주요 플랫폼은 단순 프롬프트 작성보다 아래의 운영 기능에 투자하고 있다.

| 제품·프레임워크 | 확인되는 제품 방향 | 시사점 |
|---|---|---|
| Microsoft Copilot Studio | 자연어·시각적 플로우, 노드별 테스트, 이벤트·스케줄 트리거, 사람 개입, 실행 이력·실패율·분석, 환경별 거버넌스 | 빌더의 제품 단위는 프롬프트가 아니라 운영되는 업무 플로우 |
| LangGraph / LangSmith | 체크포인트, 중단 후 수일 뒤 재개, 재시도·복구 분기, 인간 승인, 상태 저장, 버전, 오프라인·온라인 평가 | 신뢰 가능한 에이전트에는 명시적 상태와 실패 처리가 필요 |
| AWS Bedrock AgentCore | 런타임, 에이전트별 ID, 게이트웨이, 정책 기반 권한, 관측성, 장기 세션, 평가 | 기업용 에이전트의 본체는 모델보다 실행·보안·관측 계층에 가까움 |
| Claude | 조직 Skill 배포·승인·버전, 플러그인, 커넥터 권한, 원격 예약 실행을 제공 | 단순 제작·공유·스케줄은 이미 Claude가 흡수하고 있어 별도 플랫폼의 차별점이 아님 |

시장 공통분모는 `Builder + Runtime + Governance + Evaluation`이다. 따라서 빌더 UI만 만들면 경쟁력이 약하고, 실행과 운영까지 하나의 제품으로 설계해야 한다.

## 회사에 존재할 가능성이 높은 생산성 블로커

부서별 업무는 달라도 다음 구조는 일반화된다.

1. 업무 정보가 메일, 메신저, 문서, 티켓, ERP 등 여러 시스템에 흩어져 있다.
2. 담당자가 정보를 복사·조회·대조해 하나의 “건”으로 조립한다.
3. 정상 건은 규칙대로 처리하지만 예외 건에는 경험적 판단이 필요하다.
4. 다른 사람의 답이나 승인을 기다리며 업무가 며칠간 멈춘다.
5. 처리 후 여러 시스템에 결과를 다시 입력하고 관계자에게 알린다.
6. 실패하거나 담당자가 바뀌면 진행 상태와 판단 근거를 다시 복원한다.

즉 가장 큰 일반화 가능한 블로커는 **문서 작성 자체보다 시스템 사이의 예외 처리와 사람 간 대기·인계**다. 이를 “Cross-system Case Resolution” 패턴으로 정의할 수 있다.

## 대표 사례: 예외 처리 에이전트 팩토리

첫 번째 주력 사례로 **예외 처리 업무**를 권장한다. 재무의 정산 불일치에서 시작하되 같은 플랫폼 패턴을 여러 부서에 재사용할 수 있다.

### 예시: 정산·청구 불일치 처리

1. ERP, 이메일 또는 티켓에서 불일치 건이 발생한다.
2. 에이전트가 청구서, 발주서, 검수 기록, 계약 조건을 수집한다.
3. 금액·수량·세율·거래처·계약 조건을 대조하고 원인 가설을 세운다.
4. 필요한 증빙이 없으면 담당자에게 요청하고 응답까지 실행 상태를 보존한다.
5. 사규와 금액 임계값에 따라 자동 처리, 담당자 확인, 상위 승인으로 분기한다.
6. 승인 후 ERP·티켓에 결과를 반영하고 관계자에게 알린다.
7. 반영 결과를 다시 조회해 실제 완료 여부를 확인하고 근거와 이력을 남긴다.

### 같은 구조로 일반화되는 업무

| 부서 | 적용 사례 | 공통 구조 |
|---|---|---|
| 재무·구매 | 청구 불일치, 비용 증빙 누락, 구매 예외 | 증빙 수집 → 규칙 대조 → 승인 → 시스템 반영 |
| HR | 입·퇴사 준비, 휴직·복직, 인사정보 변경 | 여러 시스템 작업 → 당사자 확인 → 권한별 승인 → 완료 검증 |
| IT·보안 | 접근권한 요청, 보안 알림 조사, 계정 회수 | 맥락 수집 → 위험 분류 → 승인 → 조치 → 사후 검증 |
| 영업운영 | 할인 승인, 계약 갱신, CRM 누락 보정 | 고객·계약 정보 수집 → 정책 판단 → 승인 → CRM 반영 |
| 고객지원 | 환불·보상 예외, 기술 이슈 에스컬레이션 | 요청 분류 → 증거 수집 → 정책·과거 사례 조회 → 승인·처리 |
| 법무·컴플라이언스 | 계약 검토 접수, 통제 증빙 수집 | 문서 수집 → 체크리스트 검사 → 전문가 검토 → 이력 보관 |

이 사례가 좋은 이유는 단순 요약보다 가치 측정이 명확하기 때문이다.

- 건당 사람의 처리 시간
- 평균 대기·완료 시간
- 재작업률과 누락률
- 자동 처리율과 사람에게 넘긴 비율
- SLA 위반 건수
- 승인 정책 위반 및 감사 증빙 완성도

## 추가로 일반화 가능한 사례

### 1. 반복 보고가 아닌 “마감 오케스트레이션”

주간 보고서를 생성하는 데서 끝내지 않고, 필요한 데이터를 각 시스템에서 수집하고 누락된 입력을 담당자에게 요청하며, 이상 수치를 재확인하고, 승인 후 배포까지 관리한다.

적용 범위: 경영실적, 프로젝트 주간보고, 월말 결산, KPI 리뷰, 규제 보고.

### 2. 요청 접수부터 완료까지의 서비스 데스크

자연어 요청을 분류하고 필요한 정보를 보완한 뒤, 정책에 맞는 승인자를 정하고, 여러 시스템에서 작업을 수행하고, 실제 해결 여부를 확인한다.

적용 범위: IT 요청, 데이터 추출 요청, 디자인·법무·구매 요청, 사내 제도 문의 후속 처리.

### 3. 이상 징후의 폐루프 대응

지표나 이벤트가 임계값을 넘으면 관련 데이터를 조사하고 원인 가설과 조치안을 제시한다. 승인을 받은 뒤 조치를 실행하고 지표가 정상화됐는지 검증한다.

적용 범위: 비용 급증, 매출·전환 이상, 재고 부족, 보안 이벤트, 시스템 장애.

이 세 사례의 공통점은 `Trigger → Context assembly → Judgment → Human gate → Action → Verification`이며, 이 공통 골격을 템플릿화하는 것이 플랫폼의 재사용성을 만든다.

## Claude Desktop 생태계의 한계와 추가 계층의 이유

Claude의 한계를 과장하면 안 된다. 현재 Claude는 조직 Skill 관리와 버전 승인, 플러그인 배포, 역할별 커넥터 권한, Cowork 예약 실행까지 제공한다. 따라서 아래 기능만으로는 추가 플랫폼의 근거가 약하다.

- 자연어로 지침 만들기
- MCP 도구 연결
- Skill 공유·버전 배포
- 정기적인 요약·보고서 생성
- 도구별 허용·승인 설정

추가 계층이 필요한 지점은 **대화 보조 기능과 업무 시스템의 차이**다.

| Claude 중심 사용 | 사내 실행 계층이 제공할 것 |
|---|---|
| 사용자의 대화·예약 작업이 실행 단위 | 회사가 소유하는 업무 건·큐·SLA가 실행 단위 |
| 모델이 대화 맥락에서 수행 방식을 해석 | 버전이 고정된 입력·출력·완료 조건과 상태 전이 |
| 커넥터·도구 단위 권한과 사용자 승인 | 금액, 데이터 등급, 업무 단계, 직무분리 기준의 동적 정책 |
| 한 세션 안의 수행과 결과 확인 | 며칠간의 대기, 외부 이벤트 재개, 담당자 변경, 장기 상태 보존 |
| 사용자에게 도구 실행 승인을 요청 | 단계별 승인자 지정, 대리·기한·에스컬레이션·승인 증거 관리 |
| 대화·작업 기록을 사람이 검토 | 업무 KPI, 단계별 병목, 실패 원인, 비용, 품질 추세를 운영 대시보드로 관리 |
| Skill의 보안 검사와 게시 승인 | 실제 업무 사례에 대한 회귀 테스트, 품질 기준 미달 시 배포 차단 |
| 범용 에이전트가 모든 도구를 선택 | 고위험 단계는 결정론적, 애매한 판단만 제한된 에이전트 루프 사용 |
| Claude 제품의 실행 표면에 종속 | API·이벤트·메신저·업무 시스템 등 여러 채널에서 동일 프로세스 호출 |

Claude의 예약 작업도 유용하지만 공식 문서상 각 실행은 별도 세션이고, 클라우드 예약은 계정에 저장된 파일·커넥터를 사용하며 로컬 폴더와 연결할 수 없다. 사내 플랫폼이 필요한 핵심은 단순 스케줄이 아니라 **업무 이벤트, 지속 상태, 책임자, SLA, 재시도와 보상 처리**다.

Anthropic 자체 연구도 장시간 작업에서 컨텍스트 압축만으로는 충분하지 않고, 세션 사이의 명시적 진행 상태와 작업 인계 구조가 필요하다고 설명한다. 이는 별도 하네스·상태 계층의 필요성을 뒷받침한다.

## 왜 “복잡한” 에이전트 빌더가 필요한가

정확한 표현은 **사용법이 복잡한 빌더**가 아니라 **복잡한 업무를 명시적으로 표현할 수 있는 빌더**가 필요하다는 것이다.

단순 빌더가 `목표 + 프롬프트 + 도구`만 받으면 Skill과 차이가 없다. 실제 업무를 맡기려면 다음을 표현해야 한다.

1. **상태**: 접수, 조사 중, 응답 대기, 승인 대기, 실행, 검증, 완료, 실패.
2. **혼합 제어 흐름**: 정상 경로는 결정론적으로, 판단이 필요한 구간만 ReAct 루프로.
3. **분기와 병렬 처리**: 금액·위험·신뢰도에 따른 분기, 여러 증거의 동시 수집.
4. **사람 개입**: 승인뿐 아니라 수정, 추가정보 요청, 담당자 이관, 기한과 에스컬레이션.
5. **실패 의미론**: 재시도 가능한 오류, 모델이 복구할 오류, 사람에게 넘길 오류, 보상 작업.
6. **정책**: 누가 어떤 데이터로 어떤 행동을 어느 한도까지 수행할 수 있는지.
7. **검증**: 예상 출력뿐 아니라 필수 도구 호출, 금지 행동, 근거, 최종 시스템 상태 검사.
8. **운영**: 버전, 단계별 추적, 비용 제한, 동시 실행, 중단·재개, 롤백.

LangGraph 문서가 노드 경계의 체크포인트, 오류 유형별 처리, `interrupt()`를 통한 수일 후 재개를 강조하고, Microsoft가 노드별 테스트와 실행 실패율을 제공하는 이유도 같다. 복잡성은 시각적 그래프를 멋지게 보이게 하기 위한 것이 아니라, **실패했을 때 어디서 왜 실패했고 어떻게 안전하게 이어갈지 정의하기 위해서** 필요하다.

다만 모든 비개발자에게 빈 캔버스를 제공해서는 안 된다. 권장 UX는 다음과 같다.

- 1단계: 자연어 인터뷰로 목적과 업무 사례를 수집한다.
- 2단계: 플랫폼이 검증된 업무 패턴 템플릿을 추천한다.
- 3단계: 현업 사용자는 규칙, 예외, 승인자, 완료 조건만 채운다.
- 4단계: 고급 사용자는 생성된 상태·분기 그래프를 수정한다.
- 5단계: 실제 과거 사례로 시뮬레이션하고 실패 사례를 보강한다.
- 6단계: 운영·보안 담당자가 권한과 평가 결과를 확인한 뒤 배포한다.

즉 복잡성은 플랫폼 내부와 고급 편집기에 두고, 일반 사용자는 **의도 → 템플릿 → 사례 검증** 흐름을 경험해야 한다.

## 권장 제품 구조

```text
Claude Desktop / 사내 메신저 / 업무 시스템 이벤트
                    │
              MCP·API Gateway
                    │
       사내 Agent Runtime & Case Store
     ┌──────────────┼──────────────┐
결정론적 Workflow   Agentic Loop   Human Task
     └──────────────┼──────────────┘
                    │
      사내 시스템·데이터·외부 서비스

Control Plane
- Agent Registry / Version / Ownership
- Identity / Policy / Approval / Audit
- Trace / Cost / SLA / Quality Evaluation
- Template / Test Case / Deployment Gate
```

Claude Desktop은 자연어 인터페이스와 범용 추론을 담당하고, 사내 런타임은 회사가 소유하는 업무 상태와 정책을 담당한다. 동일 프로세스는 Claude 외에도 API나 이벤트로 호출할 수 있어야 한다.

## 플랫폼의 핵심 가치 제안

### 현업 사용자에게

“내가 아는 업무 기준을 설명하고 실제 사례로 확인하면, 반복 실행되는 팀의 업무 프로세스로 만들 수 있다.”

### 조직 관리자에게

“누가 만든 에이전트가 어떤 권한으로 무엇을 실행하는지 파악하고, 승인된 버전만 배포하며, 모든 판단과 실행을 추적할 수 있다.”

### 경영진에게

“개인의 AI 활용을 일회성 생산성 개선에서 측정·재사용·통제 가능한 조직 업무 자동화 자산으로 전환한다.”

### 플랫폼팀에게

“Claude를 비롯한 모델과 채널이 바뀌어도 업무 정의, 정책, 테스트, 실행 이력은 회사의 자산으로 남는다.”

## 차별화 문장

> **Claude가 직원 한 명의 일을 잘 돕는다면, 사내 에이전트 플랫폼은 그 일을 회사가 소유하고 반복 운영할 수 있게 만든다.**

또는 더 공격적으로 표현하면:

> **우리는 또 하나의 챗봇을 만드는 것이 아니라, 자연어로 정의한 업무를 회사의 권한과 SLA 아래 끝까지 완수하는 AI 업무 운영체제를 만든다.**

## 추진 제안

### 1단계: 업무 패턴 검증

- 3개 부서에서 예외 처리 업무를 1개씩 선정한다.
- 기존 `Claude + Skill + MCP`만으로 베이스라인을 만든다.
- 장기 상태, 승인, 실패 복구, 회귀 평가가 필요한 지점을 기록한다.

### 2단계: 좁은 플랫폼 MVP

범용 그래프 빌더보다 다음 공통 골격을 먼저 만든다.

- 이벤트·수동 접수
- 업무 건 상태 저장
- 제한된 조사용 에이전트 루프
- 사람 승인·정보 요청
- 시스템 반영과 완료 검증
- 실행 추적·재시도
- 테스트 사례와 버전 배포

### 3단계: 자연어 빌더

검증된 3~5개 패턴을 자연어로 구성하게 한다. 사용자가 자유롭게 무엇이든 만들게 하기보다, 플랫폼이 질문을 통해 필수 명세를 채우고 테스트를 생성하도록 한다.

### 투자 중단 기준

다음 조건이면 복잡한 빌더 투자를 줄여야 한다.

- 대상 업무가 대부분 한 세션 안에서 끝난다.
- 쓰기 작업이나 승인 없이 문서 생성·검색이 핵심이다.
- Skill과 Claude 예약 작업만으로 성공률과 운영 요구를 충족한다.
- 부서마다 업무 구조가 달라 공통 템플릿을 재사용할 수 없다.
- 실제 업무량이 작아 플랫폼 운영비보다 절감 효과가 작다.

## 평가 지표

- **Straight-through completion rate**: 사람 개입 없이 완료된 건의 비율
- **Human touch time**: 대기 시간을 제외하고 사람이 실제 사용한 시간
- **Lead time**: 접수부터 검증된 완료까지 걸린 시간
- **Exception containment**: 플랫폼이 안전하게 해결하거나 적절히 이관한 예외 비율
- **First-pass yield**: 재작업 없이 한 번에 완료된 비율
- **Policy violation rate**: 권한·승인·업무 규칙 위반률
- **Recovery burden**: 실패 1건당 복구에 든 사람의 시간
- **Reuse ratio**: 동일 템플릿을 활용한 부서·업무 수
- **Cost per completed case**: 실제 완료된 업무 건당 모델·인프라 비용

에이전트 수, 그래프 노드 수, 생성 횟수는 성공 지표로 사용하지 않는다.
