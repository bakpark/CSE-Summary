# Agent Playground Stage Runner MVP 설계

> 작성일: 2026-10-05. 재검토일: 2026-10-06. 상태: 구현 기준. 인프라와 성능은 검증 전이다.
> 작성 기준: ASD-STE100의 원칙을 한국어에 적용했다. 공식 준수를 뜻하지 않는다.
> 관련 문서: [Agent Definition](agent-definition-design.md), [Agent Builder](agent-builder-design.md).

## 1. 목적과 책임

**Runner는 고정한 코드 버전을 격리 환경에서 실행하고 채팅으로 시험한다.**
Definition은 코드 저장·버전 고정·ZIP 생성을 담당한다.
Builder는 편집·코드 생성을 담당한다.
SDK는 그래프 실행과 대화 상태를 담당한다.
Runner는 코드를 변경하거나 생성하지 않는다.
테스트 채팅 UI는 Playground의 별도 패널로 제공한다.

### 연계 세부 계약의 확정 필요

컴포넌트의 책임과 연계 흐름은 이 문서를 따른다.
세부 계약은 구현 전에 세 문서에서 같은 기준으로 확정해야 한다.

- 연계 API의 요청·응답 필드와 오류 코드
- SDK 인터페이스의 실제 타입과 메서드 서명
- 모델·도구 ID와 환경 연결의 매핑 규칙

현재 예시와 설명은 최종 API 명세가 아니다.
이 항목은 후속 확정 사항이며 MVP 기능 범위를 추가하지 않는다.

## 2. 세션과 실행 범위

| 항목 | MVP 결정 |
| --- | --- |
| 버전 | 테스트 세션은 버전 ID 하나에 고정한다. |
| 환경 | 세션마다 고정 이미지의 컨테이너 하나를 요청 시 생성한다. |
| 대화 | 같은 JVM의 SDK 세션에서 여러 메시지를 처리한다. |
| 동시 실행 | 세션당 메시지 하나만 처리한다. 사용자·에이전트별 활성 세션은 하나다. |
| 수정본 | 기존 세션을 종료하고 새 버전의 빈 세션을 만든다. |
| 상태 | 대화와 실행 결과는 활성 세션 동안만 유지한다. |

제어 서비스는 초기 인스턴스 하나로 운영한다.
활성 세션 수에 상한을 설정한다.
여러 사용자의 세션은 별도 컨테이너로 분리한다.
시험 도구는 조회와 모킹만 허용한다.

## 3. 사용자 절차와 화면

1. Builder에서 편집본을 저장하십시오.
2. `테스트 시작`을 누르십시오.
3. 준비 상태와 버전 ID를 확인하십시오.
4. 준비가 완료되면 메시지를 입력하십시오.
5. 답변·도구 호출 요약·오류를 확인하십시오.
6. 후속 메시지로 대화를 계속하십시오.
7. 수정본을 저장한 뒤 `수정본 테스트`를 누르십시오.
8. 시험한 버전을 내려받아 개발자에게 전달하십시오.

| 기능 | 처리 |
| --- | --- |
| 준비 상태 | 준비 중·준비 완료·준비 실패를 표시한다. |
| 헤더 | 에이전트 이름, 버전 ID, 시험 도구 설정을 표시한다. |
| 입력 | 준비 완료 시 활성화한다. 실행 중에는 전송을 막는다. |
| 새 대화 | 같은 버전으로 컨테이너를 새로 만든다. |
| 테스트 종료 | 컨테이너와 진행 중 실행을 종료한다. |
| 수정본 테스트 | 새 버전의 빈 세션으로 교체한다. |
| 다운로드 | Definition의 버전 ZIP을 제공한다. |

실행 중에는 새 대화·수정본 테스트를 막는다. 테스트 종료는 허용한다.
편집본 변경은 기존 세션에 반영하지 않는다.
새 세션을 시작하면 화면의 이전 대화를 비운다.
답변은 실행 완료 후 표시한다. 토큰 스트리밍은 구현하지 않는다.

## 4. 준비와 메시지 실행

### 준비

1. 제어 서비스는 권한과 준비 중인 요청의 중복 여부를 확인한다.
2. 플랫폼 백엔드에 저장 순번과 요청 ID로 버전 고정을 요청한다.
3. Builder 생성·Definition 고정에 실패하면 기존 세션을 유지한다.
4. 성공하면 기존 세션을 종료하고 새 컨테이너를 만든다.
5. 컨테이너에 해당 버전의 파일을 전달한다.
6. 실행 어댑터는 agent.json의 SDK 버전과 이미지의 SDK 버전을 비교한다.
7. 일치하면 고정 JDK·SDK로 Java 소스를 컴파일한다.
8. 실행 어댑터는 진입점의 open을 호출하고 그래프를 준비한다.
9. 준비 성공 후 UI의 입력을 활성화한다.

사용자·에이전트 조합마다 준비 요청 하나만 처리한다.
서로 다른 사용자의 준비는 설정한 용량 안에서 처리한다.
UI는 준비 요청 전에도 요청 ID를 만든다. 재전송에는 같은 ID를 사용한다.
제어 서비스는 준비 요청의 ID·입력·상태를 메모리에 유지한다.
같은 ID로 다른 입력을 보내면 거부한다.
같은 요청 ID의 재전송은 기존 준비 상태를 반환한다.
버전 생성 성공 후 컴파일이 실패해도 버전은 유지한다.
컨테이너 생성·컴파일·그래프 준비 실패 시 새 컨테이너를 정리한다.
종료한 이전 세션은 복원하지 않는다.
용량 부족은 명확한 실패로 표시한다.
준비 중 테스트 종료도 허용한다.
종료 요청 이후 도착한 준비 완료는 입력창을 활성화하지 않는다.
생성이 완료된 컨테이너는 종료 요청 상태를 확인하고 즉시 정리한다.
준비 시간은 테스트 요청부터 코드 생성·고정·컨테이너·그래프 준비 완료까지 측정한다.

컴파일은 --release 17, -proc:none, 고정 클래스 경로를 사용한다.
Maven·Gradle 실행과 의존성 다운로드는 하지 않는다.
고정 이미지는 JDK·SDK·실행 어댑터를 포함한다.
진입점 로딩과 open도 사용자 코드 실행이므로 컨테이너 안에서 수행한다.

### 메시지

UI는 전송 전에 요청 ID를 만든다. 재전송에는 같은 ID를 사용한다.
제어 서비스는 세션별 요청을 직렬로 처리한다.
실행 어댑터는 SDK 세션의 invoke를 호출한다.
답변과 도구 호출 요약은 UI에 반환한다.
같은 ID의 요청은 기존 상태·결과를 반환한다. 입력이 다르면 거부한다.
요청 결과는 세션 종료까지 유지한다.
제어 서비스는 요청 상태 조회를 제공한다. UI는 간단한 주기 조회로 준비·실행 상태를 표시한다.
WebSocket과 이벤트 재생 저장소는 추가하지 않는다.
Runner 실행 어댑터는 준비 상태와 메시지 호출을 제공한다.
이 연결은 사내 제어 경로에서만 접근한다.

실행 오류·시간 초과·결과 불명 시 세션을 종료한다.
자동으로 메시지를 다시 실행하지 않는다.
사용자는 새 대화로 다시 시험한다.
준비 오류는 파일·행·노드 정보를 Builder UI에 전달한다.
준비 시간 제한은 180초, 메시지 실행 제한은 120초, 유휴 만료는 30분이다.
이 값은 조정할 수 있다. 실제 시간 목표는 파일럿에서 확인한다.
기본 제한은 세션당 성공 대화 20턴, 입력 6,000자, 답변 20,000자다.
Agent의 턴당 도구 호출은 최대 10회다.
한도에 도달하면 오류 또는 새 대화 안내를 표시한다. 내용을 조용히 잘라내지 않는다.
도구 결과의 전송 크기도 설정으로 제한한다.
값은 SDK 공통 설정으로 전달한다. Runner가 대화 이력을 별도로 구현하지 않는다.

## 5. 격리와 정리

사용자 코드는 제어 서비스 JVM에서 실행하지 않는다.
컨테이너는 비특권 계정과 CPU·메모리·프로세스 수 제한을 사용한다.
호스트 디렉터리와 컨테이너 관리 소켓에 접근하지 않는다.
컨테이너에는 세션 파일과 시험용 환경 연결만 제공한다.
통신은 필요한 LLM·시험 도구 Gateway로 제한한다.
플랫폼 DB와 운영 자격증명은 제공하지 않는다.
모든 요청에서 버전·세션의 소유자를 확인한다.

컨테이너에 관리 표식을 붙인다.
세션 종료·유휴 만료·장애 시 컨테이너와 임시 파일을 삭제한다.
제어 서비스 재시작 시 표식이 있는 잔여 컨테이너를 정리한다.
기존 대화는 복원하지 않는다.
UI와 일반 로그에 자격증명과 민감정보를 출력하지 않는다.

## 6. CI/CD와 구현 순서

1. 고정 이미지에서 예제 버전을 컴파일하고 실행한다.
2. 진입점 open과 여러 턴 invoke를 연결한다.
3. 제어 서비스의 세션 생성·중복 요청·종료를 구현한다.
4. Builder의 채팅·오류 화면을 연결한다.
5. 시간 제한·유휴 정리·서비스 재시작 정리를 확인한다.

플랫폼 CI는 SDK·워커 빌드와 핵심 통합 검사를 수행한다.
담당자는 검증한 이미지를 기존 Stage 배포 도구로 배포한다.
배포 시 활성 테스트 세션을 종료한다.
초기 MVP는 SDK 버전 하나와 그에 맞는 이미지 하나만 지원한다.
호환되지 않는 버전은 거부한다. 여러 SDK별 풀은 운영하지 않는다.
편집 테스트는 CI 서버와 이미지 빌드를 호출하지 않는다.
서비스 배포는 인계받은 개발자가 기존 CI/CD로 수행한다.

## 7. 완료 기준과 제외 범위

- 고정한 버전에서 두 턴 이상의 대화를 진행한다.
- 편집본 변경이 진행 중 세션에 영향을 주지 않는다.
- 두 사용자의 대화와 코드 상태가 분리된다.
- 같은 요청의 재전송이 세션 또는 메시지 실행을 중복 생성하지 않는다.
- SDK 불일치·컴파일 오류·시간 초과·결과 한도 초과를 확인하고 다시 시험한다.
- 준비 중 종료 요청 이후 세션이 활성화되지 않는다.
- 종료·만료·재시작 후 컨테이너가 남지 않는다.
- 파일럿 코드의 준비가 180초 이내에 완료된다. 실패는 성능 성공으로 계산하지 않는다.

준비 풀, 컴파일 캐시, 분산 큐, 체크포인트, 장애 복원은 제외한다.
공유·과거 대화 조회·자동 회귀 검증·운영 자동 배포도 제외한다.
MVP는 기존 컨테이너 기반을 사용한다. 새 Kubernetes 운영 플랫폼을 구축하지 않는다.
