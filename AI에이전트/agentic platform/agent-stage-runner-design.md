# Agent Playground Stage Runner MVP 설계

> 작성일: 2026-10-05. 수정일: 2026-10-06.
> 상태: 저장 → Agent CI → 사내 Registry → Stage Runner 경로를 반영한 구현 초안. Jenkins·Nexus와 수동 새 세션 전환으로 확정했다. 저장소 주소·인증 설정·인프라·성능은 확인 전이다.
> 관련 문서: [Agent Definition](agent-definition-design.md), [Agent Builder](agent-builder-design.md).

## 1. 목적과 책임

**Runner는 CI가 등록한 고정 Agent JAR를 격리 환경에서 실행하고 채팅으로 시험한다.** 편집된 소스를 Runner에서 다시 컴파일하지 않는다.

| 담당 | 책임 |
| --- | --- |
| Builder | 편집·그래프 검사·Java 구성 코드·진단 위치 생성 |
| Definition | 편집본·불변 소스 버전 저장, 빌드·등록 산출물 메타데이터 |
| Agent CI 연계 | 저장 완료로 빌드 요청, 고정 소스 컴파일·검증, 사내 Registry 등록·결과 전달 |
| Runner 제어 서비스 | 준비된 버전 선택, 정확한 JAR 확보·검증, 세션·컨테이너·메시지·정리 |
| Runner 실행 어댑터 | SDK 일치·진입점 확인, JAR 로딩·open/invoke·결과 전달 |
| SDK | 그래프 실행·공통 노드·대화 상태·환경 연결 |

## 2. 저장부터 Stage 반영까지

1. Builder는 편집 그래프와 Java 노드 파일을 서버에 저장한다.
2. 저장 완료 이벤트를 기존 백엔드의 빌드 요청에 연결한다.
3. Builder가 해당 순번의 그래프를 검사·생성하고 Definition이 소스 버전을 고정한다.
4. Jenkins Agent CI는 고정 소스·Java 17·SDK 한 버전으로 컴파일하고 생성 계약을 검증한다.
5. 플랫폼 고정 작업으로 Agent JAR를 만들고 사내 Nexus에 불변 버전으로 등록한다.
6. 인증된 결과 경로에서 버전 ID·buildId·SDK 버전·artifactRef·SHA-256과 진단을 연결한다.
7. 등록 산출물 존재·일치 확인 후 해당 라이브러리를 실행 가능한 버전으로 표시한다.
8. Runner는 시험 요청의 정확한 버전으로 JAR를 준비하고 새 세션에서 실행한다.

미완성 그래프는 저장할 수 있다. 검사·생성 실패는 빌드 준비 오류로 표시하고 CI 컴파일·등록을 진행하지 않는다. Java 문법 오류는 CI 실패로 표시한다. 저장 성공과 라이브러리 준비 성공은 다르다.

CI는 사용자 Maven·Gradle 파일이나 임의 빌드 스크립트를 받지 않는다. 플랫폼이 관리하는 고정 파이프라인과 SDK 클래스 경로를 사용한다. 컴파일에는 --release 17과 -proc:none을 적용하고 SDK만 승인된 사내 경로에서 고정 버전으로 가져온다. 게시 POM은 플랫폼 템플릿으로 생성하며 사용자 POM을 받지 않는다. Agent JAR에는 에이전트 클래스와 manifest를 넣고 SDK·사용자 외부 라이브러리를 중복 포함하지 않는다. 사용자 노드 실행 검증은 Stage 격리 환경에서 수행한다. CI에서 사용자 코드를 자격증명이 있는 제어 프로세스로 실행하지 않는다.

Registry 게시 권한은 CI 게시 단계에만 둔다. Runner 제어 서비스는 허용 Registry의 읽기 경로로 정확한 산출물을 받아 검사한다. 사용자 컨테이너에 게시·Registry 자격증명을 전달하지 않는다. CI는 Jenkins, 라이브러리 저장소는 Nexus를 사용한다. Nexus Maven 저장소를 전제로 하며 실제 repositoryId·GAV 규칙·Jenkins job·credential ID는 사내 운영 설정을 확인한다.

## 3. 세션과 새 버전 반영

| 항목 | MVP 기준 |
| --- | --- |
| 버전 | 한 세션은 성공한 source version·buildId·artifactRef 하나에 고정한다. |
| 환경 | 세션마다 고정 런타임 이미지의 컨테이너 하나를 요청 시 생성한다. |
| 대화 | 같은 JVM의 SDK 세션에서 여러 메시지를 처리한다. |
| 동시 실행 | 세션당 메시지 하나, 사용자·에이전트별 활성 세션 하나다. |
| 저장 중 빌드 | 기존 시험 대화는 기존 JAR로 유지한다. |
| 수정본 반영 | 새 라이브러리 READY 후 사용자가 수정본 테스트를 누르면 새 세션을 만든다. 자동 전환하지 않는다. |
| 상태 | 대화·실행 결과는 활성 세션 동안만 유지한다. 빌드 결과 메타데이터는 별도로 보관한다. |

새 JAR가 등록돼도 기존 JVM에서 코드를 교체하지 않는다. 새 대화는 같은 JAR로 새 컨테이너를 만들고 CI를 다시 호출하지 않는다. 빌드 실패나 오래된 완료 이벤트로 새 버전을 성공 표시하지 않는다.

제어 서비스는 초기 인스턴스 하나다. 준비 중을 포함한 활성 세션 상한을 둔다. 여러 사용자는 컨테이너를 분리한다. 시험 도구는 조회·모킹만 허용한다.

## 4. 화면과 실행 계약

사용자는 저장 → 빌드·등록 상태 확인 → 테스트 시작 → 준비 완료 → 메시지·후속 메시지 → 수정·저장·재빌드 → 수정본 테스트를 수행한다. Builder 제작 대화와 시험 대화는 분리한다.

| 화면 | 동작 |
| --- | --- |
| 저장 | 변경 있음·저장 중·완료·실패를 표시한다. |
| 라이브러리 | 빌드 준비·대기·빌드·등록·READY·실패를 저장 순번·버전·buildId와 연결한다. |
| 테스트 시작 | 해당 저장본의 등록 JAR가 READY인 경우만 허용한다. |
| Runner 준비 | 준비 중·완료·실패를 빌드 상태와 구분한다. |
| 헤더 | 에이전트·버전·buildId·시험 설정을 표시한다. |
| 메시지 | 준비 완료 시 활성화하고 실행 중 추가 전송을 막는다. |
| 오류 | CI 컴파일 진단은 고정 버전의 노드·본문 행으로 표시한다. 로딩·open·invoke는 시험 오류로 표시한다. |
| 종료·전환 | 실행 중 새 대화·수정본 테스트는 막고 종료는 허용한다. 새 세션은 빈 대화다. |

### 준비

제어 서비스는 권한·준비 요청 중복·빌드 READY 여부를 확인한다. Definition의 버전과 artifactRef를 조회하고 허용 Registry에서 JAR를 확보해 SHA-256·SDK·버전 연결을 검증한다. 이 사전 확인이 실패하면 기존 세션을 유지한다.

사전 확인 성공 후 기존 세션을 종료하고 새 컨테이너에 검증된 JAR·시험 환경을 전달한다. 어댑터는 SDK·진입점 인터페이스와 무인자 생성자를 검사하고 컨테이너 안에서 로딩·open을 수행한다. 성공 후 채팅 입력을 연다.

컨테이너·로딩·open 실패는 새 자원을 정리한다. 종료한 이전 세션을 복원하지 않는다. 같은 준비 ID·입력은 기존 상태를 반환하고 다른 입력은 거절한다. 종료된 준비의 늦은 응답이 새 세션을 만들지 않는다.

### 메시지

UI는 전송 전에 요청 ID를 만들고 재전송에 같은 ID를 사용한다. 제어 서비스는 세션별 요청을 직렬로 처리한다. 같은 ID·입력은 기존 상태·결과, 다른 입력은 충돌이다. 다른 신규 메시지는 실행 중 BUSY로 거절한다. 결과는 세션 종료까지 유지한다.

어댑터는 같은 SDK 세션의 invoke를 호출한다. 최종 답변·도구 요약을 완료 후 전달한다. invoke 오류·시간 초과·결과 불명은 세션을 종료하며 자동 재실행하지 않는다. 기존 세션의 지연 응답은 새 화면에 표시하지 않는다.

## 5. 시간과 격리

Runner 준비 제한 180초, invoke 제한 120초, 유휴 만료 30분을 기본값으로 두고 조정할 수 있다. CI 대기·빌드·등록은 별도로 기록한다. **CI 시간을 제외한 Runner 준비 측정만으로 기존 편집 후 180초 준비 목표를 달성했다고 판단하지 않는다.** 파일럿에서 저장 후 라이브러리 READY까지와 Runner 준비 시간을 함께 보고한다. 사용자 클릭 대기는 시스템 준비 시간에서 구분한다.

컨테이너는 비특권 계정·CPU·메모리·프로세스 제한을 사용한다. 호스트 폴더·관리 소켓에 접근하지 않는다. 검증된 JAR와 세션 시험 연결만 전달한다. 통신은 필요한 LLM·시험 Gateway로 제한하고 플랫폼 DB·운영 도구·Registry 자격증명은 전달하지 않는다. 모든 요청에서 버전·세션 소유자를 확인한다.

종료·유휴 만료·장애·배포 시 관리 표식의 컨테이너와 임시 파일을 정리한다. 재시작 시 잔여 자원을 정리하고 기존 대화는 복원하지 않는다. UI·일반 로그·JAR·manifest에 자격증명을 넣지 않는다.

## 6. CI/CD 구분과 구현 순서

| 경로 | 처리 |
| --- | --- |
| 플랫폼·SDK CI | SDK·런타임 이미지·UI·제어 서비스를 빌드·발행한다. |
| Agent CI | 편집 저장의 고정 소스로 JAR를 빌드·검증하고 사내 Nexus에 등록한다. |
| Stage 시험 | 성공한 정확한 JAR를 받아 세션에서 실행한다. 재컴파일·재등록하지 않는다. |
| 목적조직 배포 | 같은 Agent JAR·SDK를 서비스에 적용하고 기존 CI/CD로 배포한다. |

구현 순서는 저장·고정 → CI 요청 → 고정 빌드·등록 → 결과 연결 → JAR 준비·세션 실행 → UI·오류 → 전체 경로 검증이다. Agent 코드 편집으로 플랫폼 이미지를 다시 빌드하지 않는다. 기존 CI·Registry·컨테이너 기반을 사용하며 새 Kubernetes 운영 플랫폼을 만들지 않는다.

## 7. 완료 기준과 제외 범위

- Java 코드 변경 저장이 고정 버전의 CI 빌드와 등록으로 연결된다.
- buildId·소스 버전·SDK·Registry JAR·체크섬이 일치한다. 중복·위조·오래된 결과를 거절한다.
- 빌드·등록·다운로드 실패를 READY로 표시하지 않는다. 현재 세션을 잘못 교체하지 않는다.
- Runner와 샘플 서비스가 같은 Agent JAR로 같은 의미의 두 턴·분기·코드 결과를 확인한다.
- 새 버전 등록과 진행 중 세션의 버전을 구분한다. 수정본 시험은 새 JAR의 빈 세션이다.
- SDK 불일치·CI 컴파일·체크섬·로딩·시간 초과 오류를 확인하고 수정·재빌드·재시험한다.
- 종료·만료·재시작 후 관리 자원이 없다. 준비 목표는 CI 대기·등록을 포함해 평가한다.

준비 풀·캐시·분산 큐·체크포인트·장애 복원·승인 승격·공유·과거 대화·사용자 회귀 시험 관리·운영 자동 배포는 제외한다. 사용자 ZIP 다운로드는 현재 작업 계획에서 제외한다. Agent CI·Registry 경로는 이번 사용자 요구에 따라 MVP에 포함한다.
