# Agent Playground 사용자 시나리오 초안

> 목적: 에이전트 제작자와 인수 개발자의 작업 흐름을 정리하고, 기능 요구사항과 개발 티켓을 구체화할 기준을 마련한다.
> 상태: 사용자 시나리오의 큰 틀을 검토한 초안. 세부 시나리오와 1차 기능 범위는 추가 확정이 필요하다.
> 작성일: 2026-10-05. 수정일: 2026-10-06.
> 관련 문서: [제품 범위 및 개발 계획](agent-playground.md), [방향 제안과 판단 근거](agent-playground-decisions.md).

핵심 흐름은 **제작자가 만들고 검증한 에이전트를 인수 개발자가 같은 산출물로 기존 서비스 안에서 실행하는 것**이다. 제작 단계의 실행 로직을 서비스에서 다시 구현하는 부담을 줄이고, 서비스의 권한·데이터·도구 연결은 별도로 검증한다.

방향 제안 문서의 구현 권고안은 확정사항으로 취급하지 않는다. 이 문서는 사용자 작업과 기대 결과를 먼저 정의한다. 기존 티켓 초안에서 삭제한 AP-01·03·21·23·22·11·04·28은 복원하지 않는다. 다만 티켓 삭제와 기능 제외는 구분하며, 인계에 필요한 최소 경로는 아래 시나리오에서 검토한다.

## 사용자와 목표

| 사용자 | 상황 | 달성하려는 결과 |
| --- | --- | --- |
| **에이전트 제작자** | 업무와 기대 결과를 이해하는 비개발자. 자연어로 제작을 요청하고 흐름·프롬프트·도구 설정을 변경한다. | 개발자의 반복 지원 없이 에이전트를 제작·실행·수정하고, 검증한 버전을 인계한다. |
| **인수 개발자** | 기존 Java·Kotlin 서비스에 에이전트를 적용한다. 서비스의 인증·DB·도구 연결과 배포를 담당한다. | 제작 단계의 실행 로직을 다시 구현하는 부담을 줄이고, 검증한 산출물을 서비스 안에서 실행한다. |

**제작자의 흐름:** 업무 설명 → 초안 제작·편집 → 저장 → Jenkins 빌드·Nexus 등록 → 시험·검증 → 인계 버전 지정

**인수 개발자의 흐름:** 버전·산출물 확인 → SDK 적용 → 서비스 연결·검증 → 기존 절차로 배포 → 변경 버전 반영

## 에이전트 제작자 시나리오

### C-01 자연어로 에이전트 초안을 만든다

**상황:** 수행할 업무와 사용할 수 있는 도구는 정해졌지만 에이전트는 없다.

1. 제작자는 업무 목적, 입력, 기대 결과와 처리 조건을 자연어로 설명한다.
2. 제작 기능은 지원 범위 안에서 에이전트 정의와 필요한 코드를 만든다.
3. 제작자는 생성된 흐름과 도구 설정을 확인한다.
4. 부족한 정보나 지원하지 않는 요구가 있으면 내용을 확인하고 요청을 수정한다.
5. 초안을 저장한다.

**완료 결과:** 다시 열어 편집하고 실행할 수 있는 초안이 생긴다. 생성 실패나 미지원 요구를 성공으로 표시하지 않는다.

**범위 제안:** 자연어 제작 진입점은 하나만 제공한다. CCAB를 재사용하는 경로와 별도 제작 경로를 모두 개발하는 범위는 잡지 않는다.

### C-02 업무 흐름과 프롬프트 및 도구 설정을 수정한다

**상황:** 생성된 초안의 분기 조건이나 응답 방식이 업무 의도와 다르다.

1. 제작자는 현재 흐름을 확인한다.
2. 자연어 또는 UI로 지원하는 변경을 요청한다.
3. 변경될 흐름과 설정을 확인하고 적용하거나 취소한다.
4. 수정 결과를 저장한다.

**완료 결과:** 자연어와 UI에서 수정한 내용이 같은 에이전트 정의에 반영된다. 잘못된 연결이나 설정은 저장·실행 전에 확인할 수 있다.

**범위 제안:** 파일럿 필수 노드·연결·조건·프롬프트·도구 설정으로 제한한다. Java 코드 내부 로직의 UI 편집과 임의 코드의 UI 역변환은 제외한다.

### C-03 공통 환경에서 테스트 입력으로 실행한다

**상황:** 저장한 초안이 의도대로 동작하는지 확인하려 한다.

1. 제작자는 편집본을 저장하고 해당 순번의 Jenkins 빌드·Nexus 등록 상태를 확인한다.
2. 라이브러리가 READY인 버전으로 테스트를 시작하고 테스트 입력을 넣는다.
3. Runner 준비·실행 상태와 답변·실행 버전·buildId를 확인한다.
4. 빌드·등록·JAR 로딩·시험 실패를 구분해 원인을 확인한다.
5. 새 버전을 저장·빌드해도 기존 대화는 유지한다. 수정본 테스트를 누르면 새 JAR의 빈 세션으로 전환한다.

**완료 결과:** 로컬 Docker 설정 없이 테스트할 수 있다. 결과가 어느 버전에서 나온 것인지 구분된다.

**시간 기준:** 저장 후 Jenkins 대기·빌드·Nexus 등록과 시험 요청 후 Runner 준비를 각각 측정한다. CI 시간을 제외한 Runner 측정만으로 기존 180초 준비 목표를 달성했다고 판정하지 않는다. 사용자 클릭 대기와 전체 업무 수행 시간은 구분한다. 95%의 요청이 30초 안에 시작한다는 수치는 아직 설계 목표다.

### C-04 실패 원인을 확인하고 수정 후 다시 실행한다

**상황:** 응답이 기대와 다르거나 도구 호출이 실패했다.

1. 제작자는 실행 결과에서 실패한 단계와 오류를 확인한다.
2. 입력·도구 호출·결과를 확인해 업무 설정 문제인지 외부 연결 문제인지 구분한다.
3. 수정 가능한 흐름·프롬프트·설정을 변경한다.
4. 같은 테스트 입력으로 다시 실행한다.

**완료 결과:** 제작자는 자신이 수정할 부분과 개발자 지원이 필요한 부분을 구분할 수 있다. 수정 전후 결과를 각각의 버전과 연결해 확인한다.

**범위 제안:** 단일 실행의 단계·도구 호출·오류 조회를 우선한다. 별도 분석 대시보드나 자동 원인 분석은 요구하지 않는다.

### C-05 검증한 버전을 인수 대상으로 지정한다

**상황:** 필수 테스트를 통과한 에이전트를 개발자에게 전달하려 한다.

1. 제작자는 인계할 버전을 지정한다.
2. 해당 버전에서 사용한 검증 사례와 결과를 정리한다.
3. 개발자에게 검증한 버전의 Nexus Agent JAR 좌표·SDK 버전과 필요한 고정 소스 위치를 전달한다.
4. 이후 초안을 수정해도 인계한 버전은 유지된다.

**완료 결과:** 개발자가 인수할 버전과 검증 근거가 명확하다.

**전달 경로:** 개발자가 같은 Nexus Agent JAR·SDK를 서비스에 적용한다. 소스가 필요하면 플랫폼 담당자가 기존 저장소의 고정 파일을 수동 전달한다. 전용 공유 링크·ZIP 내보내기 화면은 제외한다.

## 인수 개발자 시나리오

### D-01 인계받은 버전의 구조와 실행 조건을 확인한다

**상황:** 제작자가 검증한 에이전트를 서비스에 적용하라는 요청을 받았다.

1. 개발자는 지정된 버전의 정의와 노드 코드를 확인한다.
2. 입력·출력, 필요한 도구·설정, SDK 버전과 검증 사례를 확인한다.
3. 제작 환경에서 사용한 연결 중 서비스 환경에서 교체할 항목을 식별한다.

**완료 결과:** 실행 로직, 서비스 연결 작업과 알려진 제한사항을 구분할 수 있다. 별도 설명을 받아야만 실행 조건을 알 수 있는 상태를 줄인다.

### D-02 기존 Java 및 Kotlin 서비스 내부에서 실행한다

**상황:** 에이전트를 기존 서비스의 요청 처리 흐름에 넣으려 한다.

1. 개발자는 Nexus의 지정된 Agent JAR와 고정 SDK를 서비스에 적용한다.
2. 서비스의 LLM·도구 연결과 필요한 설정을 제공한다.
3. 서비스 코드에서 입력을 전달하고 실행 결과·오류를 처리한다.
4. 상태 저장이 필요한 경우 서비스의 DB 연결을 제공한다.

**완료 결과:** 별도의 Python 실행 서비스나 원격 실행 API 없이 기존 JVM 서비스 안에서 실행한다. 서비스의 Spring 버전을 바꾸지 않고 적용할 수 있다.

**요구 조건:** JDK 17 이상, Spring에 의존하지 않는 호출 방식, 생성 코드의 임의 외부 라이브러리 추가 제한. 상태 저장이 포함되면 서비스가 제공하는 `DataSource` 사용을 검토한다.

### D-03 제작 단계의 검증 사례를 서비스 환경에서 다시 확인한다

**상황:** SDK 적용은 끝났지만 인증·데이터·도구 연결이 제작 환경과 다르다.

1. 개발자는 인계받은 검증 사례를 서비스 환경에서 실행한다.
2. 상태 전이·분기·도구 호출·업무 결과를 확인한다.
3. 연결 차이로 발생한 오류를 수정한다.
4. 통합 검증 결과를 기록한다.

**완료 결과:** 제작 단계에서 검증한 흐름이 서비스 환경에서도 의도대로 수행된다.

**판정 기준:** LLM 응답 문구의 완전한 일치보다 업무 결과·분기·도구 호출의 의미가 일치하는지 확인한다. Stage 검증 통과만으로 서비스 검증을 대체하지 않는다.

### D-04 제작자가 개선한 버전으로 교체한다

**상황:** 서비스 적용 후 제작자가 흐름이나 프롬프트를 개선했다.

1. 개발자는 새 버전의 변경 내용과 검증 결과를 확인한다.
2. 필요한 서비스 연결 변경이 있는지 확인한다.
3. 새 버전으로 통합 검증한다.
4. 기존 서비스 배포 절차로 반영한다.
5. 문제가 발생하면 이전 산출물 버전으로 되돌릴 수 있는지 확인한다.

**완료 결과:** 에이전트 흐름을 서비스 코드로 다시 구현하지 않고 새 산출물을 반영한다. 제작자의 초안 수정이 운영 서비스에 즉시 적용되지는 않는다.

### D-05 중단된 실행을 같은 버전으로 재개한다

**상태:** 조건부 시나리오.

**상황:** 사람의 승인을 기다리거나 프로세스 종료 후 업무를 이어가야 한다.

1. 실행 상태와 재개에 필요한 정보를 저장한다.
2. 중단한 실행을 같은 에이전트 버전으로 불러온다.
3. 승인 또는 복구 조건을 확인하고 다음 단계부터 재개한다.
4. 동일 작업의 중복 실행·중복 쓰기가 발생하지 않는지 확인한다.

**완료 결과:** 이미 완료한 업무를 불필요하게 반복하지 않고 이어서 처리한다. 호환되지 않는 상태나 버전으로는 재개하지 않는다.

**범위 판단:** 방향 제안 문서의 중요 설계 항목이지만, 1차 필수 여부는 파일럿의 승인·복구 흐름에 따라 결정한다. 버전을 되돌리는 것과 진행 중 실행의 상태를 복원하는 것은 별도 요구다.

## 서브 결제 파일럿 시나리오

플랫폼 기능과 구분해 업무 수행 여부를 검증한다. 구체적인 결제 작업은 업무 담당자와 확정한다.

| ID | 시나리오 | 기대 결과 |
| --- | --- | --- |
| P-01 | 정상 입력으로 합의한 서브 결제 업무를 수행한다. | 기대한 답변·도구 호출·업무 처리 결과를 충족한다. |
| P-02 | 입력 누락이나 업무 조건 불충족을 처리한다. | 부족한 정보를 요청하거나 합의한 예외 경로로 진행한다. |
| P-03 | 도구 실패·시간 초과·응답 유실을 처리한다. | 성공으로 잘못 안내하지 않고 확인·재시도·복구 경로를 따른다. |
| P-04 · 조건부 | 결제 쓰기 또는 사람의 승인이 필요한 작업을 수행한다. | 승인 조건과 중복 방지 정책을 충족하고 승인·처리 결과가 기록된다. |

## 1차 기능 범위 제안

| 구분 | 포함할 사용자 경험 |
| --- | --- |
| **필수 후보** | 자연어 초안 제작, 제한된 UI·자연어 편집, 저장·버전 식별, 공통 환경 실행, 단계·결과·오류 확인 |
| **인계·적용 필수 후보** | 고정 버전과 산출물 접근, 검증 사례 확인, SDK를 통한 Java·Kotlin 내부 실행, 서비스 통합 검증, 변경 버전 반영 |
| **조건부** | 체크포인트·중단·재개, 사람 승인, 결제 쓰기 중복 방지·복구 |
| **이번 초안에서 제외** | 전용 공유 링크, 전용 내보내기 화면, KPI 집계, 별도 KPAP 연동 확장, 범용 노드·편집 지원, Agent Cluster 일반 배포·운영 |

기존 플랫폼의 프롬프트·LLM·도구 기능을 사용하는 것과 별도 연동 확장 기능을 개발하는 것은 구분한다. 삭제한 연동 티켓을 그대로 복원하지 않고, 위 시나리오 수행에 필요한 연결만 확인한다.
