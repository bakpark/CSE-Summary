# ReAct 엔진과 Deep Agents 하네스

[AI 에이전트 목차](./README.md)

> 확인일: 2026-09-09. 기능 설명은 공식 문서를 기준으로 하고, 적합성·책임 경계·권장 구조는 설계 제안으로 제시한다. 특정 업무에서의 성공률이나 비용 우위를 실측한 비교는 아니다.

## 1. 먼저 실행 전략과 실행 환경을 구분한다

**Deep Agents는 ReAct 계열의 도구 호출 루프에 작업 수행 기능을 결합한 하네스다. 분산 에이전트 플랫폼 전체와 동일한 개념은 아니다.** 공식 문서도 다른 에이전트 프레임워크와 같은 핵심 tool-calling loop를 사용하면서, 실행 환경과 컨텍스트 관리 기능을 제공한다고 설명한다. [1]

| 개념 | 담당하는 문제 | 예시 |
| --- | --- | --- |
| 실행 전략 | 다음 행동을 누가 결정하는가? | ReAct, 명시적 워크플로우, 계획 후 실행 |
| 실행 루프 | 모델 호출과 도구 실행을 어떻게 반복하는가? | 종료 조건, 도구 결과 전달 |
| 하네스 | 모델이 실제 작업을 수행하도록 어떤 환경을 제공하는가? | 파일, 컨텍스트 정리, 위임, 승인 |
| 그래프 실행 기반 | 상태 전이와 실행 상태를 어떻게 다루는가? | LangGraph, 체크포인트, interrupt |
| 서비스 런타임 | 여러 실행을 어떻게 접수·배치·격리·운영하는가? | 워커, 인증, 실행 큐, 할당량, 배포 |

따라서 다음처럼 해석하는 것이 적절하다.

```text
Agent Runtime Plane
  ├─ 실행 접수·권한·세션·버전·스케줄링
  └─ 실행 구현
       ├─ Deep Agents 하네스
       ├─ 경량 도구 호출 에이전트
       └─ 명시적 그래프와 자율 실행의 조합
```

Deep Agents는 LangChain 구성요소와 LangGraph 실행 기반을 이용한다. 경량 구현이 필요하면 LangChain `create_agent`, 상세한 상태 전이가 필요하면 직접 구성한 LangGraph를 비교 대상으로 둘 수 있다. [1]

## 2. 코딩 에이전트는 ReAct 기반인가?

넓은 의미에서는 그렇다. 다만 원래 ReAct 논문의 프롬프트 형식과 현대적인 function/tool calling API는 구분해야 한다. 원래 ReAct는 추론과 외부 행동을 번갈아 수행해 새 관찰을 다음 판단에 반영하는 접근이다. 현대적인 구현에서는 구조화된 도구 호출 메시지가 행동 요청을 표현한다. [2]

```text
사용자 요청
  → 현재 상황 파악
  → 도구 선택과 인자 생성
  → 외부 환경에서 실행
  → 결과 관찰
  → 추가 행동 또는 답변
```

Claude Code의 공식 설명도 문맥 수집, 행동, 결과 검증을 반복하는 구조다. 따라서 이런 코딩 에이전트를 ReAct 계열로 분류하는 것은 타당하지만, 모든 제품이 원 논문의 동일한 알고리즘이나 내부 프롬프트를 사용한다고 단정할 수는 없다. [3]

코딩에서 차용할 중요한 요소는 반복 자체보다 **검증 가능한 환경**이다.

```text
저장소 탐색 → 수정 → 빌드·테스트 → 실패 확인 → 수정
```

이를 일반 업무에 적용한다면 테스트의 역할을 도메인 API의 처리 상태, 스키마 검증, 정책 검사, 근거 문서가 맡도록 설계할 수 있다. 모델이 완료를 선언했다는 사실을 업무 완료의 유일한 증거로 삼지 않는다.

또한 ReAct 계열이라는 이유로 모델의 상세한 내부 추론을 로그나 사용자 화면에 노출할 필요는 없다. 운영에서는 선택한 행동, 입력·출력의 필요한 범위, 승인 근거, 검증 결과를 추적하는 것이 핵심이다.

## 3. ReAct 루프를 직접 구현한다면

다음은 특정 SDK에 종속되지 않는 설명용 의사코드다. `model`과 `gateway`는 직접 정의해야 하는 어댑터이며, 운영 가능한 완제품이 아니다.

```python
async def run_turn(
    model, gateway, context, history, user_message, *, max_rounds=12
):
    if max_rounds < 1:
        raise ValueError("max_rounds must be positive")

    messages = [*history, user_message]

    for _ in range(max_rounds):
        # 인증된 context로 노출 가능한 스키마만 조회한다.
        schemas = await gateway.visible_schemas(context)
        reply = await model.generate(messages=messages, tools=schemas)

        # 도구 호출이 포함된 assistant 메시지를 먼저 보존한다.
        messages.append(reply.as_message())

        if not reply.tool_calls:
            return {"status": "completed", "messages": messages}

        for call in reply.tool_calls:
            # 계약: 인자 검증, 현재 권한 재검사, timeout 적용.
            # 변경 작업에는 별도의 영속적 operation/멱등성 계약이 필요하다.
            result = await gateway.execute_checked(context, call)
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": result.as_json(),
            })

    return {"status": "limit_exceeded", "messages": messages}
```

중요한 기본 조건은 도구 호출과 결과의 ID를 연결하고, 도구 호출을 포함한 assistant 메시지를 누락하지 않는 것이다. 위 예제의 `max_rounds`는 모델 판단 횟수만 제한한다. 한 번의 응답에 여러 도구 호출이 있으면 총 도구 호출 수는 더 많을 수 있다.

이 루프만으로 다음 문제가 해결되지는 않는다.

| 추가 요구 | 별도 설계가 필요한 이유 |
| --- | --- |
| 상태 저장과 재개 | 어느 단계까지 확정됐는지, 입력이 중복 반영됐는지 판단해야 한다. |
| 도구 오류 처리 | 입력 오류, 재시도 가능 오류, 권한 거부, 결과 불명 상태를 구분해야 한다. |
| 비용·시간 제한 | 모델, 도구, 요약, 자식 에이전트의 총 사용량을 합산해야 한다. |
| 컨텍스트 관리 | 긴 이력과 큰 도구 결과를 모델 입력에 계속 누적할 수는 없다. |
| 사용자 승인 | 대기 상태, 승인 대상 인자, 재개 시 권한을 연결해야 한다. |
| 분산 실행 | 중복 전달, 동일 세션의 동시 실행, 워커 장애를 다뤄야 한다. |
| 외부 변경 작업 | 타임아웃 후 실제 성공 여부와 중복 실행 방지를 확인해야 한다. |

직접 구현의 비용은 단순한 반복문의 길이가 아니라, 이러한 실행 계약을 유지하는 데서 발생한다. 기본 루프의 코드 줄 수를 기준으로 프레임워크 도입 여부를 판단하지 않는 편이 좋다.

## 4. Deep Agents를 범용 기본 하네스로 채택할 때

### 장점

**도메인별 구현의 출발점을 통일할 수 있다.** 도메인 팀은 루프를 매번 만들기보다 도구 계약, 지침, 지식, 평가 기준에 집중할 수 있다. 플랫폼 팀은 공통 실행 경험과 관측 기준을 정하기 쉬워진다.

**탐색 중에 경로가 바뀌는 작업과 잘 맞는다.** 조사 결과에 따라 다음 검색이나 분석을 선택하는 업무는 모든 경로를 미리 나열하기보다 제한된 자율 실행 구간으로 구현하는 편이 자연스러울 수 있다. 반대로 처리 순서가 이미 정해진 업무에서는 이런 자유도가 불필요할 수 있다.

**긴 작업의 주변 기능을 재사용할 수 있다.** Deep Agents는 파일 기반 작업 공간, 컨텍스트 요약·외부 저장, 서브에이전트, 메모리와 승인 연동 등의 기능을 제공한다. 구체적인 기본 활성화 여부와 설정 방식은 사용 버전에 따라 확인해야 한다. [4]

**실행을 확장할 연결 지점이 있다.** LangChain 미들웨어를 통해 모델 호출 전후와 도구 실행 경계에 기능을 추가할 수 있다. 이를 이용해 공통 로깅과 정책 어댑터를 설계할 수 있다. [5]

### 단점과 주의점

**지연시간과 비용의 편차가 커질 수 있다.** 모델 판단과 도구 실행을 반복할수록 경로별 호출 수가 달라진다. 단순 조회까지 항상 장기 작업 하네스로 처리할 필요는 없다. 실제로 얼마나 느려지는지는 모델, 활성 기능, 입력, 도구 성능에 따라 측정해야 한다.

**기본 하네스의 가정에 맞춰야 한다.** 파일·위임·컨텍스트 기능을 거의 사용하지 않는 업무라면 기본 기능을 제한하는 설정이 오히려 복잡해질 수 있다. 이 경우 `create_agent`로 필요한 미들웨어만 조합하는 대안이 있다. 일부 핵심 미들웨어는 제거에 제약이 있으므로, 모든 기능을 뺀 것을 단순히 “minimal DeepAgent”라고 가정하지 않는다. [1][6]

**모델 변경이 전체 실행 환경의 호환성을 보장하지 않는다.** 주 실행 모델, 요약 모델, 자식 모델, 도구 스키마 지원, 구조화 출력, 토큰 계산을 함께 검증해야 한다. 모델 API가 호환된다는 이유만으로 장기 작업의 품질까지 같다고 볼 수는 없다.

**요약과 위임에도 정보 손실 가능성이 있다.** 설계상 긴 원문을 압축하거나 자식의 결과만 받는다면, 원래 근거로 돌아갈 경로를 남기는 편이 좋다. 요약을 사실의 유일한 원장으로 사용하지 않는다.

**보안과 업무 정합성은 별도 책임이다.** 프롬프트에 필수 순서를 적는 것과 서버가 그 순서를 강제하는 것은 다르다. 도구를 숨기는 것, 승인 대화가 있었던 것, 체크포인트가 존재하는 것만으로 권한과 멱등성이 완성되지 않는다.

**공통 하네스 변경의 영향 범위가 커진다.** 프롬프트·미들웨어·도구·모델 변경을 버전으로 기록하고, 대표 업무에 대한 회귀 평가를 거쳐 배포하도록 제안한다.

## 5. 대안은 두 축으로 비교한다

### 실행 전략

| 전략 | 다음 행동 결정 | 잘 맞는 문제 | 설계 부담 |
| --- | --- | --- | --- |
| ReAct형 자율 실행 | 매 단계 모델 | 탐색, 조사, 예외가 많은 문제 해결 | 종료·비용·권한 통제 |
| Plan-and-execute | 계획 생성 후 단계별 실행과 재계획 | 여러 하위 과제로 분리되는 작업 | 잘못된 계획 수정, 실행 결과 검증 |
| 명시적 워크플로우 | 코드의 상태 전이와 분기 | 필수 순서, 규칙적인 처리 | 예외 분기와 상태 설계 |
| 혼합형 | 고정 흐름 안의 자율 구간 | 업무 절차와 탐색이 함께 필요한 서비스 | 자율 구간의 입출력 계약 |

이들은 상호 배타적이지 않다. 계획의 각 단계를 ReAct로 실행하거나, 그래프의 일부 노드에 자율 에이전트를 넣을 수 있다. 멀티 에이전트 역시 ReAct의 대체 알고리즘이라기보다 실행 주체를 나누는 별도 축이다. 워크플로우와 에이전트의 제어 방식 구분은 LangGraph 공식 가이드에서도 다룬다. [7]

### 구현체

아래 적합성은 기능과 책임 범위를 바탕으로 한 설계 판단이지, 성능 순위가 아니다.

| 선택 | 얻는 것 | 직접 부담할 부분 | 우선 검토할 상황 |
| --- | --- | --- | --- |
| 모델 SDK로 루프 직접 구현 | 좁고 명확한 실행 핵심 | 컨텍스트, 재개, 오류, 관측 등 주변 기능 | 요구가 작거나 실행 방식이 매우 특수함 |
| LangChain `create_agent` | 도구 호출과 미들웨어 기반 구성 | 필요한 하네스 기능의 선택·조립 | 제한된 도구를 쓰는 경량 업무 |
| Deep Agents | 장기 작업에 필요한 기능을 묶은 하네스 | 기본 구성 이해, 정책 경계, 버전 검증 | 조사·코딩·복합 업무의 기본 구현 |
| 직접 구성한 LangGraph | 명시적 상태 전이와 혼합형 구현 | 그래프·상태·마이그레이션 설계 | 필수 절차가 있는 업무 |
| OpenAI Agents SDK | 에이전트, 도구, 핸드오프 등의 구성요소 | 서비스 환경에 맞는 저장·격리·운영 연동 | 다른 실행 SDK와의 비교 실험 |
| Claude Agent SDK | Claude Code 계열의 루프와 작업 도구 재사용 | Claude 중심 통합과 실행 환경 | Claude 기반 코딩·작업 에이전트 |

OpenAI Agents SDK와 Claude Agent SDK의 제공 범위는 각각의 공식 문서를 참고한다. SDK에 세션 기능이 있다는 사실만으로 분산 실행의 모든 요구가 충족된다고 해석하지 않는다. [8][9]

## 6. 권장하는 책임 경계

```text
도메인 팀
  도구 계약 / 지식 / 프롬프트 / 완료 판정 / 평가 데이터

Agent Runtime Plane
  인증 / 프로필 버전 / 실행 접수 / 동시성 / 예산 / 감사

Agent Engine 및 Harness
  모델 판단 / 도구 호출 연결 / 컨텍스트 관리 / 위임

도구 실행 경계와 도메인 시스템
  현재 권한 / 자원 소유권 / 승인 검증 / 멱등성 / 업무 상태
```

예를 들어 주문 취소 상담은 에이전트가 의도를 파악하고 필요한 정보를 질문하되, 실제 취소 API가 대상 주문의 소유권·취소 가능 상태·사용자 확인·중복 실행 여부를 검증하도록 설계한다.

명시적 그래프가 유용한 업무는 그래프로 만들고, 도메인 복합 API 하나로 통제할 수 있는 업무는 도구로 제공한다. 모든 업무를 그래프화할 필요도, 모든 절차를 모델에 맡길 필요도 없다.

초기부터 다수 SDK를 완전히 추상화하는 거대한 계층을 만들 필요는 없다. 우선 공통 실행 계약과 프로필 스키마를 분리하고, 실제 필요가 확인된 실행 구현을 추가하는 편이 낫다. 서로 다른 엔진 간 체크포인트의 자동 이식은 별도의 문제다.

## 7. 도입 전 비교 실험

같은 업무 데이터·모델·도구·예산을 기준으로 경량 루프, Deep Agents, 명시적 워크플로우를 비교하도록 제안한다.

대표 업무는 단순 조회, 탐색형 조사, 실제 상태 변경으로 나눈다. 정상 요청뿐 아니라 도구 실패, 권한 부족, 중복 요청, 사용자 중단, 워커 재시작도 포함한다.

평가 기준은 업무 성공률, 검증된 완료 여부, 최초 유의미한 응답 시간, 전체 완료시간 p95, 성공 건당 비용, 불필요한 호출, 정책 위반, 중단·재개 결과다. 응답 문장이 자연스럽다는 이유로 업무에 성공한 것으로 처리하지 않는다.

**최종 제안은 Deep Agents를 범용 기본 하네스의 유력한 후보로 두되, 유일한 실행 방식으로 고정하지 않는 것이다.** 동적 프로필과 분산 실행에 적용하는 방법은 다음 문서에서 다룬다.
